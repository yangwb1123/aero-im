### 各方向的架构评估

#### 方向一（P1 · 搜索质量）—— 稳健

该方向是目前这组中最扎实的。它很好地识别了搜索体验中确实缺失的部分。有两个细微调整建议：

- **BK-tree 拼写纠错 → 考虑 SymSpell 替代**：BK-tree 在编辑距离 ≤2 时足够好，但 SymSpell 会更高性能（预处理成本摊平，恒定时间查找）。由于你的 FTS 已经索引了 unigram，你可以在启动时直接从 `pg_trgm` 统计信息中构建 SymSpell 字典。无新增依赖。
- **MMR 多样性重排 → 注意分页一致性**：文档中提到了种子多样性用于分页一致性，这是正确的。但在 `merge_hits` 中实现 MMR 需要小心——如果第 1 页多样性剔除了一些高分结果，用户翻到第 2 页时不应再次遇到它们。需要一个 `exclude_ids` 参数。

#### 方向二（P2 · 已读回执隐私）—— 建议范围更广

这是一个简单、高影响力的功能。但架构分析遗漏了一个重要的边缘情况：

- **消息发送者视角的「幽灵已读」**：当发送者看到「已读：Alice, Bob」时，如果 Charlie 隐藏了他的回执，发送者无法区分「Charlie 没看到」和「Charlie 隐藏了」。文档说「这是一个特性，不是 bug」——我赞同这一选择，但**消息发送者侧 UI 应标记此限制**，例如添加一个工具提示：「还有 3 人已读但选择不显示」。

- **缺少工作区级别的强制执行**：方向二正确地考虑了工作区级别 `force_read_receipts = true`。但还需要考虑**合规性**：在法律保全/审核场景中，管理员可能需要覆盖用户的回执首选项。`legal_holds` 表已经存在（在 AGENTS.md 的 4.3 中提及），因此可以扩展：受法律保全约束的用户的 `read_receipts` 可以被静默忽略。

#### 方向三（P2 · 自适应削峰）—— 架构上最复杂；精简范围

这是架构上最雄心勃勃的方向，但也是风险最高的——因为实时流量调节中的故障可能比它试图解决的过载雪崩更严重。

**具体风险**：
1. **PG 池使用率不是负载的好指标**：Postgres 连接池在 Postgres 开始排队之前就已经是满的。到池使用率达到 80% 时，你可能已经处于过载状态。考虑使用 `pg_stat_activity.wait_event` 或查询延迟（p50/p99）作为主要信号。
2. **降速因子传播延迟**：如果使用了 `AtomicF64`（如建议），就要注意在 JVM 以外的平台上，`AtomicF64` 在 Rust 中不可用（需要 `AtomicU64` 的位转换）。使用 `Ordering::Relaxed` 可以，但需要仔细记录文档。
3. **关键 vs 非关键的二分法过于粗糙**：文档将「动画状态查询」标记为非关键。但在直播场景中，流动画状态查询是 UI 的关键路径。考虑**三层制**（critical / normal / best-effort），而非二元制。

**精简单范围建议**：从**仅限 PG 延迟感知**开始。这是最具影响力的单一信号。省略 CPU/内存/NATS pending——它们会增加复杂度，但在像 tokio 这样的异步运行时中相关性较低（epoll 循环感知不到「CPU 过高」；tokio 只是变得更慢）。

#### 方向四（P2 · 知识图谱）—— 价值最高，但体量被低估

文档说「后端体量: L（~800 新 Rust 行）」。这低估了。

考虑实际所需：
1. AI 提示工程与调优（提取提示不是一次就行的——你需要添加示例、处理幻觉、设计系统提示以抑制噪音） ← 未计入
2. 实体合并（当「Project Alpha」和「Project Alfa」被 LLM 提取时——如何处理同义词？）
3. 实体规范化（「John Smith」「John」「Smith, John」——需要规范化为规范形式）
4. 消息编辑（消息被编辑时更新实体？文档未说明）
5. 删除级联（现有 `ON DELETE CASCADE` 工作正常，但需要向用户确认：删除消息是否应该从知识图谱中移除实体？）

**实际体量估计**：~1500–2000 行 Rust + 前端 + 测试，包括所有边缘情况。

**但方向四是这四个方向中差异化潜力最大的**。没有主流协作平台做自动知识图谱。Slack 的 Canvas 是手动文档。Teams 的 Wiki 是手动维基。

方向四也是唯一一个需要 AI 及时性 SLA 的方向——如果 AI worker 队列深度为 1000，实体提取可能在消息发送后几分钟才完成。在这几分钟内，用户可能已经搜过该消息，却发现知识图谱标签缺失。考虑：
- **近实时回退**：如果 AI worker 繁忙（预算为 0 或队列深度 > 500），则跳过 AI 提取，改用确定性提取器（正则表达式 + 命名实体识别词表）。这将捕获「#project-name」「@person」「$amount」等，而无需 AI。
- **针对该意图启用不同预算权重**：提取（1）应该比摘要（3）更便宜且优先级更高。

#### 方向五（P3 · 搜索自动补全前端）—— 正确的依赖顺序

方向五正确地将自身定位为方向一的 UI 消费端。但应注意：**自动补全本身不需要方向一就能工作**。`POST /api/search/suggest` 可以建立为房间/参与者名称的简单前缀查询，外加从 `search_click_events` 表获取的热门查询——完全不需要 AI。因此方向五可以且应该先于方向一部署，作为独立的 UX 改进。

### 排期修正

方向五（搜索前端）应从 P3 提升至 P2。原因：
- 它可以在零后端新代码的情况下工作（纯前端自动补全，基于房间/参与者名称前缀查询）
- 它是用户每天都会遇到的直接影响 UX 的问题
- 它不需要方向一即可落地

建议的排期：

| 冲刺 | 方向 | 理由 |

| 冲刺 A | 方向二（已读回执隐私） | ~100 行后端 + 1 次迁移；高影响力，低风险 |
