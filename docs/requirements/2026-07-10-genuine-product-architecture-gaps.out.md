## 总体评价

这份文档的质量和系统性强于 `docs/requirements/` 中绝大多数既有分析。关键在于两点：**每个方向都有代码证据表的映射**，且**前置覆盖边界表**确实干净——「BFF vs 客户端一致性」「搜索质量 vs 搜索交互」「AI 后端能力 vs 客户端消费面」三组区分做得很精准，没有重复既有覆盖。

但需要指出几个值得重新审视的判断：

---

## 方向一：REST/WS 双源一致性 —— 评级应下修至 P2

**我不同意 P1 的判断。理由是：**

启动竞态条件（1a）在当前代码中**已经被隐含处理**——`handleIncomingMessage` 的 `arr.some(x => x.id === m.id)` 去重检查确实存在，且 `listMessages` 响应通过 `state.messagesByRoom[roomId] = msgs` 赋值前，已有的 WS 消息已经存在于数组中。你说「覆盖整个数组」是准确的，但**覆盖意味着相同 id 的消息会保留最后一次赋值**——如果 WS 先到、REST 后到，WS 消息不会丢失，只是被 REST 的同 id（带更多字段）版本替换。丢失只发生在极端情况：消息在 WS 到达和 REST 响应之间被创建且**WS 先通知、REST 分页不包含它**（游标边界）。这个窗口在实际使用中非常窄。

**真正有价值的子问题**是 1c（REST 无缓存）和 1b（全量重渲染），但这俩是性能优化而非数据正确性问题。建议下调为 P2，合并到「客户端性能优化」方向。

---

## 方向二：管理 SPA —— 体量评级准确，但切入路径有更优解

XL 体量是准确的。但有一个架构决策未在文档中讨论：**管理 SPA 应该与 IM SPA 共用 WS 连接吗？**

文档暗示「两个独立的 WS 连接」——但这意味着管理操作（如批量删消息、修改频道留存）产生的 `RoomEvent` 需要被管理 SPA 实时感知。如果管理 SPA 用自己的 WS 连接（不同 `participant_id`），需要管理员在房间中作为参与者才能收到事件，而管理操作往往发生在管理员**不在**房间上下文中的情况。

**更好的切入角度**：管理操作应该通过 REST 完成 + 管理 SPA 使用**轮询或独立的管理 WS subject**（`admin.events.{ws_id}`），而非复用 IM 的 `im.room.*` subject。这个区分值得在提案中明确。

---

## 方向三：消息行交互增强 —— 体量被低估

你标注 M，但让我逐项加总：右键菜单（~100 行）+ 键盘导航（~200 行）+ 多选模式（~200 行）+ 固定交互（~150 行）+ 跳转上下文（~100 行）+ 引用视觉（~80 行）= **~830 行纯 JS**。对于当前 `web/` 总代码量 ~5.9K 行，这是 **14% 的增长**。而且其中右键菜单和多选模式涉及**跨模块状态共享**（`context.js`、`app.js`、`render.js` 三处改动），不是纯粹增量添加。

更关键的是：这些交互改动需要与既有 hover 操作栏（`wireMsgActions`）的**交互优先级**对齐——右键菜单和 hover 栏同时可见时，用户应看到哪个？多选模式下 hover 栏是否隐藏？这些决策需要 UX 规范而非纯代码。**体量应调整为 M-L（或 L）**。

但论点「消息行交互是使用频率最高的 UI 表面」是准确的，P2 评级合理。

---

## 方向四：AI 客户端整合 —— 最大的 hidden gem

这是五个方向中**性价比最高的**。如你准确指出，`smart_replies.rs`、`translate.rs`、`ai_rewrite.rs` 的 API handler 已经完整实现且经过服务端测试——前端整合只需要 API 调用 + UI 渲染，零后端工作。

但我发现一个**你文档中没提到的额外切口**：`agent_bot.rs` 的 @提及 AI 助手响应目前以纯文本消息返回。如果智能回复和翻译按钮在消息行上线，用户可以在 AI 助手回复上点击「翻译」——这是一个跨功能组合机会（AI 助手返回英文 → 用户一键翻译为中文），不需要任何新 API。

**建议文档补充这个交叉点**，作为方向四和方向三之间的协同效应证据。

**P2 评级准确。** 建议在方向一和方向五之后优先启动。

---

## 方向五：数据生命周期 —— 时间窗口判断有误

你说「提前规划数据生命周期是成本架构」——我同意论点，但**建议时间窗口从「应最先启动」后移**。

理由：当前代码有三个事实与你的紧迫性假设矛盾：
1. `migration 0148` 分区 shadow 依然**未启用**（你准确指出）
2. `retention sweep` 设置了 `deleted_at` 但永不清扫物理行
3. 存储监控仪表板目前不存在

这意味着在迁移 0148 分区启用 + 物理删除管道建立之前，冷热分层是**打地基阶段**，无法在工程上交付。而启用分区 + 物理删除是独立于冷热分层的工作——应拆为两个阶段：**Phase 1**（分区启用 + 物理软删冷却周期清扫，P1）→ **Phase 2**（冷热分层 + S3 归档，P2）。

Phase 1 体量不大（~300 行 Rust + 一条启用分区的迁移），可以真的排在 P1。Phase 2 才是 XL 体量的冷热分层。文档当前把两者混为一个 XL 方向，建议拆开。

另外，**数据量估算表缺少关键的「软删占比」维度**：如果 60 亿消息中有 30 亿被软删，物理删除 Phase 1 可以回收 ~50% 存储而不需要冷层。这是一个低成本高收益的第一步。

## 跨方向观察

**五个方向之间有 3 个我看到的拮抗关系（trade-off），文档未提及：**

1. **方向一（RoomStore 缓存）vs 方向五（冷热分层）**：如果 RoomStore 实现了 LRU 缓存 + stale-while-revalidate，冷层查询延迟（~500ms）对缓存的第一次 miss 影响更大——用户从热层切换到冷层时，第一次请求可能触发 `CacheStore` 的 fetch + S3 读取双重延迟。需要 RoomStore 在缓存 fetch 之前区分热/冷请求。

2. **方向二（管理 SPA）vs 方向四（AI 交互）**：管理 SPA 需要显示 AI 用量仪表板（`GET /api/ai/usage`），而方向四的智能回复/翻译调用会增加用量。如果管理 SPA 先建设，它会暴露 AI 使用数据给运营团队——运营团队会基于数据推动方向四的优先级。这两个方向的时间顺序值得协调。

3. **方向三（右键菜单）vs 方向四（消息上下文 AI）**：右键菜单的「对此提问」是方向四场景 4 的前置条件。如果方向四先于方向三启动，AI 上下文入口的交互载体缺失。两者应该**同批次**落地，或者方向四的「消息提问」入口先借用 `msg-actions` 中的按钮（而非右键菜单）。
