**整体判断**：这是我目前在仓库中看到的最有穿透力的系统级分析。前面 125+ 份文档大多聚焦「某个功能缺什么」或「哪些 API 没被 web 端调用」，而这 5 个方向是**从架构拓扑特征推导出产品路线图**——这在深度上与之前所有文档不是一个量级。

具体亮点：

1. **方向 1 的「不分库」论证**——你明确指出 workspace_id 贯穿全表 + COALESCE 继承链，分库会导致跨库查询爆炸。这个判断救了产品路线图的命：如果上来就按 SaaS 101 建议「每个租户一个 PG」，最后会发现 `legal_holds.sweep` 和 `retention.sweep` 全部需要跨库 UNION，工程噩梦。**每工作区连接池隔离 + 同一物理库**是正确折中。

2. **方向 3 vs 方向 4 的博弈**——你在 P1 层放了联邦（方向 3）和应用平台（方向 4），但仔细看**方向 4 的 Phase 1（命令注册表）其实可以 1 周内做完**，因为它只需要一个进程内 HashMap + 一个 GET 端点，而方向 3 需要 schema 变更 + 访问层重构。实施顺序上方向 4 Phase 1 可以插队到 Phase 1 里做——**低成本高感知**。

3. **方向 5 的「无人做到」声明**——这是对的。Slack AI 和 Teams Copilot 都是 reactive（你问才答）。主动从对话流中提取知识（决策、RFC、ADR）目前没有 IM 平台做。但有一个风险：**准确率问题**。如果提取精度不够（把「我觉得今天中午吃面」策展为决策），用户信任会一次性崩塌。建议 MVP 阶段**只对特定模式触发**（如消息含 `we decided` / `decision:` / `arch:` 等标记性前缀），不依赖 AI 分类——将 false positive 降到 0 再放 AI 分类。

4. **AGENTS.md 一致性检查**——你的分析中引用的代码路径（`retention.rs`、`background.rs`、`commands.rs`）与最新的 AGENTS.md §2 定时器清单和 §4.1 加功能配方一致。没有发现过时引用。但 `background.rs:84-100`（embedding_backfill）在最新代码中行号可能已漂移——这是 AGENTS.md §4.3 提到的已知问题。

5. **一个遗漏的交叉点**：方向 1（多租户隔离）和方向 2（数据分层）之间有一个强依赖你未明确写出——**数据分区方案依赖于租户隔离的粒度**。如果是每工作区独立 pool + 独立 `messages` 表分区，分区键可以是 `workspace_id`；如果是共享表，分区键只能是 `created_at`。建议在 Phase 1 的设计阶段就确立分区策略，否则 Phase 2 改分区方案时需要重迁移。
