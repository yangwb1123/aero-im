## 几点具体反馈

### 方向一（生产部署基础设施）—— 建议再提一级

这个不仅是 P0，从文档自身证据来看它可能是 **方向一的缺失导致方向二难以实施** 的根因（如你所写的「前置依赖」关系）。建议在文档中更明确地指出：
- 无 Dockerfile → 无法创建可复现的测试环境 → 集成测试靠手动管理数据库 → 实际上被跳过
- 无 CI → 方向二的性能回归门禁无法落地
- 无 TLS → 方向五的 WebRTC 在纯 HTTP 下不可用（`getUserMedia` 要求安全上下文）

也就是说，方向一是**阻塞性前置条件**，其他四个方向多少都依赖它。这张关系图在「跨方向设计注意事项」里提到了，但可以在**每个方向的「前置依赖」和「为什么是 PX」段落中更明确地绑定**。

### 方向二（集成测试）—— 1821:0 的数字非常有力

一个建议：可以顺带提一下**代码覆盖率**维度。既是 0 集成测试，自然没有覆盖率报告。`cargo tarpaulin` 或 `grcov` 之类的工具不在任何配置中。如果能跑出来当前纯单元测试的覆盖率（我猜大概 30-40% 核心逻辑、0% 服务编排层），数据会更完整。

另外：`bus/seq.rs` 的 `SeqGate` 去重逻辑是**最危险的未测区域之一**——at-least-once 语义靠它正确工作，但它的正确性只在单元测试里验证了单线程单进程的场景。NATS 重投、多实例并行、消费端崩溃后恢复的组合场景是单元测试无法覆盖的。

### 方向三（消息可靠性）—— 最容易被忽视的 P0

这个方向的优先级判断非常准确。大部分 IM 项目的早期版本都会犯这个错——「显示即发送」的错觉直到用户抱怨丢消息才被正视。文档中引用的代码证据（`submitComposer` 忽略 `ws.send()` 返回值）**硬核实锤**。

建议补充一个边界场景：**多标签页发送冲突**。用户打开两个标签页，在标签页 A 发送消息（optimisticAdd -> pendingByTempId），在标签页 B 看不到这条消息（因为没有跨标签页同步），又在 B 发送了同样内容。结果：
1. 两个 pending 条目各自匹配到服务端的两条消息
2. 或者因为去重逻辑导致一条丢失

这不属于 localStorage 队列能解决的问题（localStorage 在 `storage` 事件下可以跨标签页同步，但 `pendingByTempId` 是内存 Map，无法被其他标签页读取）。

### 方向四（API 治理）—— 可以关联方向三

方向四的 WS 错误帧标准化和方向三的 tempId/ack 机制可以合并设计：
```
标准 WS 错误帧:
{
  "type": "message_ack",
  "temp_id": "pending_abc123",
  "status": "rejected",
  "code": "RATE_LIMITED",
  "message": "发送过快，请稍后再试"
}
```

这样方向三需要的 tempId 映射和后端错误码标准化就一起解决了。

### 方向五（WebRTC 基础设施）—— 对 P2 的定位认同

有一个数据点可以帮助说服提升优先级：**中国网络环境下对称 NAT 的比例 > 20%**（GFW 大量使用对称 NAT）。如果目标市场是中国用户，「约 15% 的用户无法通话」在当前是静默失败——用户不会知道是 NAT 问题，只会认为「这个软件的通话功能是坏的」。这其实是一个 **产品信任的 P0 问题**，但因为是媒体层的，适合归到 P2 因为 TURN 需要成本。

建议在风险表中补充：**无 TURN 时的用户体验降级路径**——当前不是 fallback to P2P，而是完全失败+静默。甚至没有一个「对方无法接听」的错误提示。

## 一个额外发现

你的文档提到了 `AGENTS.md` §4.4 的「禁区」和 §2 的「媒体 seam」，但可以再加一条：

**NATS consumer 配置的耐久性不对称**：
- `im.room.*` 使用 durable name `aero-server`（at-least-once，重启恢复）
- `live.stream.*` 使用 ephemeral consumer（重启丢失 offset）
- bot 们使用各自的 durable name（`aero-bot`, `aero-ooo`, 等）

这意味着：如果 `run_bus_listener` 因 bug 崩溃，重启后可以接着消费（durable）；但 `run_live_bus_listener` 崩溃后重启，重启期间的弹幕/礼物/观看事件全部丢失。@提及的 `agent_bot` 也可靠（durable）。但 `go_live_bot`（开播通知）是 `live.stream.*` 上的 durable `aero-golive`？文档写的是 **queue-group durable**，需要确认这个 durable 是否真的持久化——如果是，那开播通知就不会丢；如果不是，开播通知在消费者重启期间丢失会导致用户永远收不到开播推送。

这个不对称值得在某个方向的「风险」中提及，或者作为一个独立的架构观察。
