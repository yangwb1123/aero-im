## 方向的架构评审

### §1 预测性预加载 — 架构评分 8/10

**真正的亮点**：房间切换预测 + 附件预渲染 + AI 答案预缓存这三个点的确有差异化潜力，且几乎没有产品做过。

**需要解决的关键 bug**：

1. **附件缩略图的后端基础设施缺失**：您正确指出 `BlobRepo` 无法生成缩略图。但这是一个**新的服务端图像处理管线**——需要引入 `image` crate（或调用 `ffmpeg`/`sharp`），为每个上传的文件（不只是图片，还要考虑 PDF/GIF/视频的首帧）生成 256px 缩略图，并缓存到 `blob_store`（新的 `sized_x` 路径或 `thumbnails/{id}.jpg`）。这个后端工作量可能占此方向总工作量的 **60-70%**，而非「约 200 行前端 JS + 1 个缩略图端点」。

2. **预测模型的冷启动**：新用户 / 新工作区无历史行为数据。建议初版使用**确定性规则**（最近活动时间 * 0.3 + 未读数 * 0.5 + 用户是否在其中发过消息 * 0.2），而非机器学习。

3. **预加载和现有 `switchRoom` 的状态竞争**：当预加载响应在用户实际切换房间后到达时，可能覆盖新房间的状态。需要版本戳或 `abort controller` 防止老响应覆盖新数据。

**推荐**：将此方向的 MVP 调整为**缩略图端点 + 附件预加载**（价值最大化的最小交付），房间预加载和 AI 预缓存放在 Phase 2。

### §2 NL2API — 架构评分 6/10

**产品直觉正确**，但架构方案有**几个严重缺陷**：

1. **LLM 翻译 SQL 是已知的危险模式**。您正确指出了需要白名单，但白名单模板化（`只允许预先定义的聚合模板，LLM 只填充参数`）在实际运行时有两个问题：
   - **用户查询的自然语言多样性远远超过模板的覆盖面**。「谁在这周最活跃？」、「这周谁的发言最多？」、「周活跃用户排名」可能是同一个查询，但用户不会用模板化的语言表达。
   - **LLM 往往忽略「只填充参数」指令**。Anthropic 和 GPT-4 都有在被引导到特定格式时忽略约束的倾向（prompt injection 的一种变体）。

2. **更好的架构方案**：与其把 NL2SQL 放在安全热线上，不如**将查询作为一组可枚举的分析操作**（analysis operations）而非 SQL 模板。例如：
   ```
   NL → LLM → { operation: "top_posters", params: { workspace: "current", time_range: "last_7d", limit: 10 } }
   ```
   `operation` 必须在白名单枚举中，由服务端映射到预定义 SQL。这样 LLM 永远不需要生成 SQL，只需要分类意图 + 提取参数。

3. **查询结果的可视化格式**：`{ type: "bar", labels: [...], values: [...] }` 限制了 UI 的可能性。建议使用更通用的 `{ type: "table"|"bar"|"line"|"number"|"trend" } + { columns: [], rows: [] }` 格式，前端按 type 渲染不同的可视化组件。这样 future-proof（未来增加 pie / heatmap / scatter 不需要改后端格式）。

**推荐**：将这个方向改为**参数化操作的 NL 分类**，而非 NL2SQL。MVP 只需要 5-8 个高频操作（top posters, active channels, message trend, storage usage, AI budget used, response time）。

### §3 边缘节点 — 架构评分 9/10

**问题定义最清晰**，但交付体量被低估：

1. **NATS 超级集群不是简单地加配置**：NATS Gateway 模式需要：
   - 每个区域独立的 NATS JetStream 集群（至少 3 节点/区域）
   - Gateway 配置（`gateways: [{ name: "us-east", urls: [...] }]`）
   - 跨区域 subject 的 `allow`/`deny` 配置（避免全局 subject 风暴）
   - JetStream consumer 在跨区域场景下的语义（每个区域独立 tracking？or global？）
   这不是「加几行配置」的工作量。建议在 ROADMAP 中标注**依赖 `aero-cli deploy` 自动化**。

2. **边缘 WS 代理的无状态设计**：您描述的是「轻量 WS 代理，无状态，只做 WS 终止 + 透视」。但 hub 层现在是有状态的（`subscribed_rooms`、`stream_watchers`）。推到边缘意味着要么：
   - (a) 边缘代理完全无状态，每次 WS 消息都通过 NATS 传递到中心 hub 做业务逻辑（延迟增加）
   - (b) 边缘代理携带部分状态（订阅的房间、watcher 状态），中心 hub 通过 NATS 广播状态变更
   - 推荐方案 (b)，参考 Discord 的 guild 分片模型（各区域缓存用户→房间映射，变更时中心广播 invalidation）

3. **Presence 就近读的 TTL 一致性**：`5 秒 TTL 缓存 presence` 意味着用户离开后最多 5 秒其他用户仍然看到在线。对协作工具这可能不是问题（Slack 也是类似延迟），但对直播场景（观众计数）可能不够精确。建议对不同 presence 类型设置不同 TTL（协作 5s，直播观看数 2s，通话在线 0s——走信令实时更新）。

**推荐**：将此方向标记为 P2→P3 的长期方向，拆分为：
- Phase 1：NATS Super Cluster 配置 + 跨区域 IM 消息（无 WS 代理，客户端直接连接到集群）
- Phase 2：边缘 WS 代理（需要 hub 层重构 + 无状态化）
- Phase 3：Presence 就近读 + geo-DNS

### §4 互动治理 — 架构评分 8/10

**性价比最高的方向**。几个补充观察：

1. **反应限流的 DB 支持已就位**：迁移 0118 `message_reactions` 表是独立的 `reactions` 表，有 `message_id` + `participant_id` + `emoji` 的组合唯一性。限流只需在 `reaction.rs` handler 入口加 `rate_limit.check()` 和单条消息的计数查询。预计**半天可交付**。

2. **自定义 Emoji 审批流的核心复杂性不在技术**：`workspace_emoji` 表增加 `status` 字段 + 审批 API 是简单 CRUD。复杂的是**通知工作区 Admin 去审核** + **审核通过后刷新前端 emoji picker 缓存**。需要一个新的 `RoomEvent::CustomEmojiApproved` / `CustomEmojiRejected` 变体来扇出。

3. **消息评分系统不要叫「评分」**：`rating` 在中文语境可能被理解为「星评」（类似 Amazon 商品）。建议使用**「认可」**（endorsement）或**「有用/有趣/赞」**作为产品名称，避免让用户感觉在参加考试。

4. **对照 Slack 的 emoji 治理**：Slack 在 2023 年增加了自定义 emoji 的使用限制（仅 workspace owner/admin 可上传），2024 年增加了 emoji 使用分析（哪些 emoji 被用得最多）。这说明即使 Slack 也花了多年才建立这个治理框架——Aero 有机会在第一版就建立。

**推荐**：这是 P1 中可最快交付的方向。MVP 顺序：
1. 反应限流（2 天）
2. 自定义 Emoji 审批流（1 周）
3. 互动指标 API（3 天）
4. 消息认可系统（1 周，可选，可以先不做）

### §5 自适应通知 — 架构评分 7/10

**最难的「速赢」**——技术复杂，依赖多，且收益难以量化。

关键问题：

1. **`dwell_time_ms` 的精度受前端 SDK 限制**：Web 端无法可靠追踪「通知从显示到被点击/忽略的时间」，因为：
   - 页面在后台时，`setTimeout` 被限制到 1 分钟精度
   - 用户可能在多个标签页间切换
   - 移动端 `visibilitychange` 事件在浏览器标签页切换时可能延迟 10+ 秒
   - 建议改用**事件驱动的跟踪**：`notification_shown → timer start` + `click/dismiss → timer stop`，而非计算显示时间

2. **「专注指数」的推断不可靠**：连续 30 分钟无通知点击可能表示：
   - 用户正在专注工作
   - 用户已离开座位
   - 用户的电脑合上/屏幕关闭
   - 不推送通知可能会让用户觉得「我打开了 Aero 但是没看到任何通知」更加沮丧

3. **通知摘要的语义聚合**当前不可能：`notification_bundles` 按时间窗口（比如 5 分钟内同一频道的通知聚合），不是按语义相似度。要实现「同一话题的 3 条消息→1 条摘要」，需要：
   - `self.imperial_collapse` 实际上是调用 Anthropic 做消息摘要（= 额外的 AI 成本）
   - 每 5 分钟启动一次批量摘要，每个频道每次聚合可能花 $0.01-0.05 AI 费用
   - 如果工作区有 1000 个活跃频道，每天聚合成本 = 几百美元

4. **推荐的简化 MVP**：不要一开始就做 AI 驱动的自适应调度。MVP 应该是：
   - 行为数据收集（`PATCH /api/notifications/:id/interaction` + 存储 `clicked/dwell_ms`）
   - **规则决策**而非 ML 决策：「某类通知 7 天内被该用户忽略了 80%+→自动降级一档」
   - 用户可见的「通知瘦身」控制：「过去 7 天你忽略了 43 条 reaction 通知，要静音此类通知吗？」（一键确认）
   - 这个 MVP 约 2 周，IM 层面 AI 调度推迟到 Phase 2

**推荐**：拆为 3 个独立阶段：
- Phase 0（P1，1 周）：行为数据收集 + 前端通知中心增强（分组/过滤）
- Phase 1（P2，2 周）：规则驱动的自动降级（无视学习，基于历史忽略率）
- Phase 2（P3，3 周）：AI 驱动的调度优化 + 通知摘要
