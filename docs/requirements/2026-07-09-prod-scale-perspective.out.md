### 🔍 关于方向 I：Blob 分发

你关于 `blob_download` 缺少缓存头的分析是**正确的，影响重大**：

```rust
// 当前（~line 1750, routes.rs）
// 无 Cache-Control, 无 ETag, 无 Last-Modified, 无 304
```

但我想补充一个你遗漏的设计约束：

**所有 blob 下载都会先进行 `blobs.is_accessible_by()` 的 PG 查询**。由于 `If-None-Match`/`304` 逻辑必须发生在鉴权*之后*（否则你会出现信息泄露：被拦截的 304 会确认 blob 的存在），所以：

```
请求 → 速率限制 → PG 读取元数据 → PG 鉴权 → 读取 blob_store → 返回 200（或 304）
```

与以下内容对比：

```
请求 → 速率限制 → 读取 blob_store 元数据 → 检查 If-None-Match → 不调用 PG → 返回 304
```

对于公开可访问的 blob（头像、表情、OG 预览），304 优化可以完全绕过 PG 往返。对于私有 blob，你仍然需要执行 PG 鉴权，然后才能决定是返回缓存内容还是新内容。

**建议：为 `sha256` 是公共知识（公开 blob）的 blob 添加一个快速的 blob_store 元数据读取 → ETag 匹配 → 短路路径。**

### 🔍 关于方向 III：生产自愈

分析正确——`background.rs` 确实泄露了 `tracker.spawn` 的异步块，并且当 any `run_bus_listener` 退出时只有日志行。

一个额外的观察结果：TaskTracker 本身*确实*提供了一个 `wait().await` 来检查所有任务是否已完成——但只有在关闭时。它不提供针对早期退出的监控。因此，一个通用的 `TaskSupervisor` 是有意义的。

然而，我对 consumer lag 自动暂停的建议持**谨慎态度**：

> Consumer lag > 10k → 暂停消费

暂停消费者意味着积压会*增长得更快*（NATS 主题保留策略会在此窗口期间丢弃旧消息）。一个更好的策略是：

- **Lag > N → 触发告警 + 增加消费并发**（如果消费者在可用的处理能力下延迟）。
- **Lag > M 且持续处理时间 > T → 逐步降级**（排除非关键处理的批次——例如，moderation skip，transcribe skip）。
- **Lag > L 且趋势加速 → 触发 L7 负载削减**（为现有 WS 连接维持扇出，但拒绝新连接）。

如果暂停消费者是最后的手段（在 `num_unprocessed > max_possible` 时，它正在丢失消息），但肯定不是默认的缓解措施。

### 🔍 关于方向 IV：多租户隔离

这是分析中最薄弱的环节，恕我直言。虽然*概念*是合理的，但实际影响有资格区别：

#### 已被覆盖的防御

在分析中表示为 red flag 的一些资源维度实际上已经有了防御措施：

| 资源 | 文档说 | 实际 |
|------|-------|------|
| WS 连接 | ❌ 每工作区无上限 | 每个工作区没有*显式*配额，但`hub.rs` 在扇出时不区分工作区。确实是一个缺口。 |
| Blob 大小 | ❌ 每工作区总量无限制 | 存在 32 MiB 限制。每工作区的限制确实缺失。 |
| PG 连接池 | ❌ 单池，所有工作区共享 | *这实际上是正确的设计*。在应用层进行 PG 连接池分区会导致资源利用效率低下。正确的做法是使用 `PgPool` 的 `max_connections` 设置（在 sqlx 级别）并通过 `SKIP LOCKED`/`pg_stat_activity` 监控每个连接。 |
| 请求并发 | ❌ 全局 `max_concurrency` | 全局 `ConcurrencyLimitLayer` 存在于 `serve.rs` 中——但确实是全局的，不是每工作区的。 |

#### 实际问题：哪个层在哪里？

配额强制要求做出痛苦的架构决策：在 Rust 路由器代码中，还是通过中间件/代理（例如，Kong/Envoy per-route 速率限制）？

```
选项 A: 在 Rust 路由器中强制（就像你建议的那样）
  优点：可以访问业务上下文（工作区 ID、角色、订阅层级）
  缺点：必须由每个路由处理程序检查；在关闭或迁移期间容易出错

选项 B: 在基础设施层强制（Envoy 速率限制过滤器 + Redis）
  优点：在 Rust 代码到达之前拒绝请求；进入/退出矩阵清晰
  缺点：不知道工作区边界；需要基于 JWT 声明进行路由
```

对于 `max_members`/`storage_quota_bytes`（慢速变化的资源），应用程序级别的强制措施是可以的。对于 `messages_per_min`（高频），基于 Envoy/Proxy 的强制措施更好。

**建议：按资源类型划分策略——</TEXT>** 静态资源（成员、房间、存储配额）→ 应用程序层（缓存在 Redis 中），高频资源（消息速率、WS 连接）→ 基础设施层（Envoy/gateway），或者将两者结合使用双桶方案。

3.  **最大的收益（P0，1 天）**：WS 集成测试框架。一个 Rust 集成测试二进制文件，它：
    - 连接到 WS `ws://localhost:8080/ws?token=xxx`

    - 断言接收到的帧包含 `{"type": "presence", ...}`
    - 发送 `{"type": "send_message", ...}`
    - 断言接收到的帧包含 `{"type": "message", ...}`

    这将捕获端到端路径中的回归——序列化 → 总线 → 扇出——这是 841 个单测无法覆盖的。
