# Async & Data Reviewer — Message Recall (消息撤回)

**Deviation note:** `prompts/README.md` and `ui-specs/engineering/{async-data,form-table-state,error-recovery,defect-patterns}.md` do not exist in this repo (searched repo root, `ui-specs/`, `docs/`; only `.claude/worktrees/*` copies of the design spec exist). The review below stands on the evidence supplied plus direct source inspection of `web/app.js`, `web/ws.js`, `web/render.js`, `web/context.js`, `web/delivery_cursor.js`, and the server side they depend on (`aero-storage/src/message/query.rs`, `authorization.rs`, `events.rs`, `ws_impl/backfill.rs`). Where I cite "decision tables", I map to the decision-table concepts enumerated in the attack checklist (stale-response prevention, convergence, idempotency, retry matrix, single source of truth).

Scope: the client-side async surface of recall — WS frame handling, out-of-order/redelivery ordering, change-replay convergence, optimistic/reliable-delivery interplay, render terminality. Server defects are included only where they defeat or are defeated by client logic.

## What's actually good (verified, not assumed)

- **Frame contract**: `app.js:98` wires `msg:recalled`; server contract test `recalled_frame_shape_carries_placeholder_message` (`ws/frame.rs:226`) pins `type:"recalled"` + `recalled_at`/`recalled_by` + placeholder body. Wire name, seq stamping, and SeqGate dedup (`ws.js:299`) all line up.
- **Out-of-order ordering guard** (`app.js:300-321`): shared `lastEditAt` order key is *sound under current server invariants* — recall doesn't bump `edited_at` (`authorization.rs:300-311`), and user edits are blocked post-recall (`messages.rs:391`), so `edited_at` < `recalled_at` always holds for a recalled message. Stale edit after recall → dropped; stale recall after delete → resurrect guard. Correct.
- **Terminal render** (`render.js:708-800`): placeholder rendered as content (not "已删除"), `· 已撤回` meta, actions row (react/reply/edit/delete) suppressed for recalled messages.
- **`applyChange` precedence** (`app.js:324-330`): tombstone → recall → edit; handles a both-recalled-and-deleted row correctly. Client is *ready* for change-replay recalls.

The problems are convergence, one staleness hole in the insert path, and a feature-completeness gap.

## Cross-cutting notes (no action here, record only)

- DB-architect F2 (rolling-deploy old nodes ack-drop `recalled` events) compounds Finding 1: clients on an old node never get the frame and — because replay never delivers recalls — never converge until reload. Deploy ordering matters more than usual here.
- The completion report's "all clients render the placeholder" (assumptions) and "与既有编辑/删除同一不变量" (design要点) claims are both false: the first per Finding 1, the second per Finding 2 (`edit_outboxed_system` shares the row but not the terminal-state fence). The testing reviewer's honesty audit caught this; I confirm it from the client side.
- Compliance Findings 1/2 (member-visible pre-recall history; deferred-erasure predicate) are server/data-layer; the client renders history rows as-is, so no frontend action.
- Checklist items 1 (debounce/throttle), 3 (duplicate submit), 4 (retry matrix), 8 (error mapping) are N/A today purely because no recall UI exists — they become mandatory with Finding 4's fix; the 409→success mapping in particular.

## Verdict

The client-side ordering/seq/resurrect machinery is genuinely well-built and the wire contract is pinned by tests — but two reproduced defects break the feature's core promise ("recalled content stays gone for every viewer") and the web SPA cannot initiate a recall at all.

**VERDICT: FAIL — (1) change-replay never delivers recalls (`changes_since` predicate omits `recalled_at`), and the client's id-dedupe drops the current-state placeholder row on cursor replay, so offline/reconnecting clients keep original content indefinitely and `applyChange`'s recall branch is dead code (P2, reproduced); (2) `edit_outboxed_system` has no `recalled_at` fence, so a system edit after recall broadcasts a fresh `edited_at` that the client's timestamp guard legitimately accepts — original content resurrects on every connected client (P1, reproduced); (3) the SPA has no recall entry point (`ws.js`/`api.js`/`render.js` — receive-only), so the feature is not end-to-end from the web client. The client guard design is correct and reusable; both blocking defects are fixable with the server predicate/fence fixes plus a single application-funnel check in `handleIncomingMessage`.</｜｜DSML｜｜parameter>
