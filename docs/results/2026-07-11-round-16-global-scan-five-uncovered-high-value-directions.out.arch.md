# 架构分析报告：Aero IM 第 16 轮全局扫描评述

---

## 1. 架构评估

### 1.1 当前架构的核心优势

**事件驱动骨架的选择是恰当的。** Aero IM 本质上是一个实时协作平台——消息、弹幕、通话信令、推送通知、审核管道全部以事件为第一公民。NATS JetStream 作为跨实例事实源（durable consumer 保障 at-least-once），Hub 作为进程内扇出层（bounded mpsc），这一分层清晰地分离了「跨节点可靠传递」与「进程内高效广播」两个关注点。

**值得保留的关键设计信号：**

| 设计决策 | 理由 | 风险 |
|----------|------|------|
| NATS 按 subject 分区（`im.room.*` vs `live.stream.*`） | 自然隔离 IM 和直播的扇出规模、消费语义（durable vs ephemeral） | subject 爆炸——若 room 数量达百万级，NATS 路由表压力需监控 |
| Hub 不承担跨节点逻辑 | 保持了进程内扇出的轻量性，避免 Hub 变成上帝对象 | 无 |
| Redis 作为集群状态的事实源（presence/roster/call roster） | 避免进程内存漂移；sorted-set 天然支持 TTL 驱逐 | Redis 不可用时降级策略缺失 |
| str0m 纯 Rust WebRTC 栈 | 避免对 libwebrtc 的 C++ 依赖，编译和部署简化 | str0m 0.19 仍在快速演进，API 稳定性需关注 |

### 1.2 架构债务与技术债

**方向 ⑤（Schema 演化安全管线）的 P1.5 升级是精准的判断。** 157 次零回滚迁移是项目最大的单一技术债。让我展开：

**① 零外键约束（方向 ③ 已识别）——这是设计决策，不是疏忽。** 代码库注释提到「application-enforced referential integrity」，但缺乏自动核对机制意味着数据腐烂只有在用户报告时才被发现。这是一个**可接受的权衡**，前提是配套了核对定时器（方向 ③ 阶段 A）。

**② 迁移管线缺失回滚能力——这是真正的技术债，不是设计决策。** 理由：生产 DDL 故障的 MTTR 取决于手工构造回滚 SQL 的速度，而手工构造在高压下极易出错。没有 `down.sql` 意味着：
- 回滚不是一等公民（无法自动化测试）
- expand-migrate-contract 模式无法实施
- staging 回滚演练不可执行

**③ at-least-once 语义的幂等覆盖不一致。** 文档 §4.2 明确要求「付费/外发/计费副作用须有幂等键」，但 `golive_bot` 被标注为「非幂等（重投插重复行）」。这种不一致意味着随着重投发生，动态 feed 会出现重复条目。要么接受（文档已声明），要么修复。目前是已知债务。

**④ 模块间偶合模式。** `ImService` 既编排消息逻辑又调用 `assert_room_access`（后者本质上是鉴权职责）。这导致 `ImService` 的测试需要构造完整的参与者和房间上下文。一个潜在的改进是将鉴权守卫提取为中间件层，但需要评估是否值得为当前规模引入额外抽象。

**⑤ 媒体 seam 的「已建+已测，生产未接线」状态。** 这是务实的——在无真实媒体对端的情况下，单元测试验证了结构正确性，CI 不跑端到端媒体测试。这不是债务，而是正确的分阶段交付策略。

## 2. 扩展方向

基于输入文档的分析，结合我自身的判断，以下是 5 个高价值架构扩展方向：

---

### 方向 A：可观测性基建 → 混沌工程就绪

**为什么需要：** 文档正确指出 at-least-once NATS delivery 的 RTO 从未被测量过。在一个有 150+ REST 路由、20+ WS 帧类型、持久总线 consumer、SFU 媒体管道的系统中，故障模式呈组合爆炸。单元测试覆盖 happy path + 部分 error path，但**分布式系统的可靠性只能通过受控故障实验验证**。

**核心挑战与技术难点：**
- Toxiproxy 在 Rust 集成测试中的使用模式不成熟（主要生态在 Ruby/Go）
- NATS 故障注入需要模拟 JetStream consumer 重平衡延迟
- WS 客户端重连 + `since` 游标追赶的端到端测试需要真实时间推进

**预期的架构变更：**
- `storage/db.rs` 添加 `AtomicBool` 故障开关（模拟 DB 不可用）
- `hub.rs` 添加 `try_send` 故障注入点（模拟扇出瓶颈）
- 集成测试套件添加 `tests/chaos/` 目录，运行在独立的 Docker Compose 环境

**对现有系统的影响：**
- 故障开关默认关闭，无性能影响
- 需要 CI 添加 chaos 测试 stage（并行运行，不阻塞主流水线）
- 建议阶段 A（单元级故障模拟）2-3 天，不依赖外部工具

---

### 方向 B：集中式身份事件审计（方向 ② + ③ 的交集）

**为什么需要：** 输入文档的「被遗漏的战略联系」第一条是金子。密码重置、邮箱变更、2FA 启用/禁用、恢复码生成——这些事件当前不被审计。对于合规要求严格的企业客户（SCIM 入站供给已经存在），身份事件的可审计性是采购门槛。

**核心挑战与技术难点：**
- 审计事件需要不可篡改（append-only + 签名链？或者仅 append-only？）
- 审计事件的保留策略（与消息 retention 不同的生命周期）
- 审计事件本身的可观察性（谁在审计审计日志？）

**预期的架构变更：**
- 扩展 `audit_events` 表的 `event_type` 枚举
- 在 `auth/change_email.rs`、`auth/reset_password.rs`、`twofa.rs` 添加审计写入点
- 添加审计事件查询 API（仅 admin）

**对现有系统的影响：**
- 低侵入性——`audit_events` 表已存在，仅需扩展枚举和写入点
- 建议 1-2 天实现

**决策点：** 是否需要审计链（Merkle 树 / 签名）？
- 选项 A（简单）：append-only 表，数据库中不允许 UPDATE/DELETE
- 选项 B（合规）：每条事件包含前一条的 hash，定期签名
- **建议：** 阶段 A 选 A，阶段 B 选 B。企业合规需求通常只要求 append-only，签名链是加分项

---

### 方向 C：数据核对框架（方向 ③ 阶段 A 的具体化）

**为什么需要：** 零外键约束的设计决策是合理的，但代价是跨表引用完整性只在应用层维护。一旦出现 bug（错误的条件判断、遗漏的更新路径、并发竞态），数据腐烂只能被动发现。**核对定时器是主动检测的第一道防线。**

**核心挑战与技术难点：**
- 核对查询需要全表扫描——需要在低峰期运行
- 核对结果需要去重（同一行腐烂可能被多次核对捕获）
- 自动修复逻辑必须幂等（修复可能部分失败，下次运行需继续）

**预期的架构变更：**
- 新表 `data_quality_log`（`audit_events` 的简化版，作为模板）
- 新模块 `crates/aero-storage/src/reconciliation/`，包含核对查询
- 每个核对查询对应一个 `r#”…"#` 原始 SQL，单独可测试

**核对优先级：**

| 优先级 | 核对 | SQL 模式 | 预期行数级 |
|--------|------|----------|-----------|
| P0 | room_members → participants 孤立行 | `LEFT JOIN WHERE participants.id IS NULL` | 低 |
| P0 | messages → rooms 脏引用 | `LEFT JOIN WHERE rooms.id IS NULL AND NOT deleted` | 低 |
| P1 | messages → participants 脏引用（sender_id） | 同上 | 低 |
| P1 | reactions → messages 脏引用 | 同上 | 低 |
| P2 | 通话 roster 中的孤立 entry | `call_rosters LEFT JOIN calls` | 低 |

**对现有系统的影响：**
- 只读核对查询对主库影响有限（建议配置 `pg_ctl` 语句超时）
- 自动修复默认 dry-run，手动确认后才执行写操作

---

### 方向 D：API 平台化 —— OpenAPI 优先的开发流程

**为什么需要：** 输入文档在方向 ④ 中正确指出「系统拥有丰富的外部 API 能力，但缺少让开发者发现这些能力的入口」。对于面向外部开发者的平台（Bot SDK、Webhook 管道），**API 文档是产品而非附件**。

**核心挑战与技术难点：**
- utoipa 的属性宏方式与现有路由架构不匹配（输入文档已识别）
- 150+ 路由的手工标注成本高，且易与实现不同步
- WebSocket 帧格式无法用 OpenAPI 表达（需要补充文档）

**关于 utoipa vs aides 的决策：**

| 维度 | utoipa | aides |
|------|--------|-------|
| 集成方式 | `#[utoipa::path(...)]` 属性宏 | `OpenApiGenerator` trait |
| 与 axum 的匹配度 | 需手动标注 | 更自然（`axum-extra` 可选） |
| 社区成熟度 | 高（广泛使用） | 较低 |
| 对现有代码的侵入 | 高（每个 handler 加属性） | 中（需要实现 trait） |
| 生成的文档质量 | 高（支持 `oneOf`、`anyOf`） | 中 |

**建议：** 阶段 A 使用 `aides` 做概念验证（50 个核心路由），如果验证通过则全面采用。不要一次性标注 150+ 路由——先标注 Bot API 和 Webhook 相关端点，因为这些是外部开发者最先接触的。

**预期的架构变更：**
- 新增 `crates/aero-api-docs/` crate（独立的文档 crate，避免污染 server crate）
- 或内联在 server crate 的 `docs/` 模块中
- WebSocket 帧格式使用 Markdown + JSON Schema 独立文档化

**对现有系统的影响：**
- 低侵入性——路由 handler 只需添加少量标注
- 不影响运行时性能（OpenAPI spec 在启动时生成一次）

---

### 方向 E：层次化限流 —— 从单层到多级弹性

**为什么需要：** 当前限流为单层（每个工作区/全局令牌桶）。但随着 Bot API 和 Webhook 的引入，外部开发者会以不同于人类用户的模式消费 API。单层限流无法区分：
- 恶意行为（暴力破解、爬虫）
- 合法的高吞吐（Bot 批量处理）
- 正常人类用户

**核心挑战与技术难点：**
- 多级令牌桶的协调（全局 → 工作区 → 用户/Bot）
- Bot 认证 vs 用户认证的限流档位分离
- 限流策略的热加载（不改代码调整配额）

**预期的架构变更：**
- 限流中间件重构为链式：`GlobalRateLimit → WorkspaceRateLimit → UserRateLimit`
- 每个级别可独立配置（env + API）
- 限流策略存储在 Redis 而非进程内存（支持水平扩展）

**对现有系统的影响：**
- 中等侵入性——需要重构 `rate_limiter.rs`
- 但阶段 A（仅为 Bot 添加独立限流档位）可在 1-2 天内完成
- 阶段 B（完整多级链 + 热加载）约 1 周

## 3. 接口设计建议

### 3.1 核心原则

从输入文档中提炼出的接口设计原则：

**原则一：仓储即契约。** 当前代码库中每个功能对应一个 XRepo（`MessageRepo`、`ReactionRepo`、`CallRepo`）。这个模式应该维持并严格执行——仓储层是数据库访问的唯一通道，不允许在 service 层写裸 SQL。

**原则二：事件是自治边界。** `RoomEvent` 和 `StreamEvent` 是模块间通信的契约。新增变体时必须同步更新：
- NATS 序列化/反序列化
- `Hub::fan_out_raw` 匹配臂
- WebSocket 客户端帧处理
- 前端 `ws.on('msg:...')` 处理器

**原则三：参与者参数在前。** `assert_room_access(participant, room)` 的参数顺序（参与者在前）是一个已确立的约定。新 API 必须遵守。

### 3.2 是否需要新的抽象层

**需要：OpenAPI 定义层。** 当前架构缺少一个独立的 API 契约层。建议：

```
server/src/
  routes/              # 路由注册（不变）
  handlers/            # 请求处理（不变）
  openapi/             # 新增：OpenAPI 定义
    mod.rs
    im.rs              # IM 相关端点定义
    live.rs            # 直播相关端点定义
    auth.rs            # 鉴权相关端点定义
    admin.rs           # 管理端点定义
```

`openapi/` 模块使用 `aides` 的 `#[derive(OpenApi)]` 方式组织，与 `handlers/` 一一对应但不耦合。这样可以独立演进 API 文档而不影响 handler 实现。

**不需要：额外的 service 抽象层。** `ImService` 已经是一个合理的 service 层，不应再将其拆分为 `ImReadService` / `ImWriteService` 之类的细粒度服务。当前粒度刚好。

### 3.3 向后兼容性

**API 版本化的最小可行方案：** 不要立即引入 `/v1/`、`/v2/` 路径前缀。而是：
1. 在 OpenAPI spec 中添加 `deprecated` 标记
2. 在响应头中添加 `X-API-Version: 2026-07-12`（日期版本）
3. 当需要 breaking change 时，引入新端点，旧端点标记 deprecated

这比 URL 版本化更轻量，且与 REST 最佳实践一致。

**WebSocket 帧的兼容策略：** `ClientFrame`/`ServerFrame` 枚举的 `#[serde(deny_unknown_fields)]` 应保持关闭（已如此）。添加新字段时使用 `#[serde(default)]` 提供默认值。这样旧客户端在新服务器上不会崩溃，只是可能忽略新功能。

## 4. 技术选型

### 4.1 不需要引入的新技术栈

| 提案 | 结论 | 理由 |
|------|------|------|
| **Toxiproxy**（混沌工程） | ✅ 建议采用 | 最成熟的网络故障注入工具，与 Rust 集成测试配合良好（通过 TCP 代理中断） |
| **utoipa**（OpenAPI） | ❌ 不推荐 | 属性宏方式与现有架构不匹配，见上文 aides 对比 |
| **aides**（OpenAPI） | ✅ 建议采用 | trait-based 方式更适合现有架构 |
| **Kafka** | ❌ 不推荐 | NATS 已经满足所有需求，引入 Kafka 只是增加运维复杂度 |
| **ClickHouse**（审计日志） | ❌ 不推荐 | 当前 `audit_events` 表量级不足以支撑专用 OLAP 数据库 |
| **MongoDB** | ❌ 不推荐 | SQL 是正确选择，无文档模型需求 |

### 4.2 第三方依赖的评估标准

当前代码库对依赖管理较为克制（`Cargo.toml` 中依赖项合理）。评估新依赖的标准：

1. **许可证兼容性**（当前 deny.toml 已配置，遵循即可）
2. **MSRV 兼容性**（当前 1.80，新依赖不能要求更高版本）
3. **纯 Rust vs C 绑定**：首选纯 Rust 实现（如 str0m 的选择）
4. **社区活跃度**：最近 6 个月有提交
5. **与 tokio/axum 生态的兼容性**（首选 tokio-rs 或 tower 生态下的 crate）

### 4.3 自建 vs 采购的决策依据

| 场景 | 决策 | 理由 |
|------|------|------|
| 混沌工程基础设施 | **采购**（Toxiproxy） | 自建网络代理层成本远高于采用成熟工具 |
| 数据核对框架 | **自建** | 核对查询完全依赖于 Aero IM 的数据模型，无通用工具 |
| OpenAPI 生成 | **采购**（aides） | 通用问题，不应自建 |
| 审计日志系统 | **自建** | 仅需在现有 `audit_events` 表上扩展，无复杂需求 |

## 5. 实施路线图

### 优先级排序（P0/P1/P2）

| 优先级 | 方向 | 阶段 | 工作量估算 | 理由 |
|--------|------|------|-----------|------|
| **P0** | ⑤ Schema 演化安全 | 阶段 A：为最近 10 次迁移编写 `down.sql` + `rollback` 命令 | 2 天 | 下一次 DDL 生产事故随时可能发生。157 次零回滚迁移是最高风险 |
| **P0** | ① 混沌工程 | 阶段 A：单元级故障模拟（`AtomicBool` 开关 + 集成测试） | 3 天 | 零阻塞依赖，高信心收益。建立 RTO/RPO 基线 |
| **P0** | ③ 数据质量监控 | 阶段 A：P0 核对定时器（room_members + messages） | 3 天 | 检测数据腐烂的第一道防线 |
| **P1** | ② 身份生命周期 | 审计事件 + 确认邮件 + 恢复代码 UI | 4 天 | 工作量被事实性错误高估，实际仅 4 天 |
| **P1** | ⑤ Schema 演化安全 | 阶段 B：`expand-migrate-contract` 模式 + `migration validate` 命令 | 3 天 | 构建安全管线 |
| **P1** | ① 混沌工程 | 阶段 B：Toxiproxy 集成测试 + 网络分区场景 | 5 天 | 验证 NATS 重平衡 + WS 重连 |
| **P2** | ④ API 平台化 | 阶段 A：aides OpenAPI 生成（核心 50 路由） | 1 周 | 虽然重要，但不阻塞当前功能开发 |
| **P2** | ③ 数据质量监控 | 阶段 B：自动修复（dry-run → confirm → scheduled） | 1 周 | 在核对稳定运行后引入自动修复 |
| **P2** | ④ API 平台化 | 阶段 B：WebSocket 帧格式 + Webhook 事件类型文档 | 3 天 | 平台化关键交付物 |

### 时间线（优化后）

```
Week 1：⑤-A + ①-A + ③-A（P0 并行——团队 2-3 人时可行）
Week 2：②-A + ⑤-B（P1）
Week 3：①-B（Toxiproxy 集成）

Week 5-6：③-B + ④-B + ②-B（如果需要）
```

### 风险点与缓解策略

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| `down.sql` 的逆向工程可能遗漏数据迁移 | 中 | 高 | 每个 `down.sql` 编写后由第二人审查；在 staging 环境回滚验证 |
| Toxiproxy 与 CI 容器环境的兼容性问题 | 低 | 中 | 预先在 Docker Compose 中验证；准备备用方案（代码级故障开关） |
| 核对定时器对生产库的性能影响 | 中 | 中 | 配置 `statement_timeout`；在只读从库运行 |
| aides 生态不成熟导致功能缺失 | 中 | 中 | 阶段 A 先 POC 50 路由验证；如不满足则回退到 utoipa |
| 团队对审计事件的范围有分歧 | 低 | 低 | 先实现最小可行集（密码重置 + 邮箱变更 + 2FA），后续扩展 |

### 关于输入文档的错位纠正

在实施路线图中，我采纳了输入文档的以下纠正：

1. **方向 ② 工作量减半**（从 1 周到 4 天）——密码重置和邮箱变更后端已完成
2. **方向 ⑤ 优先级提升**（从 P2 到 P1.5）——157 次零回滚迁移的实际风险
3. **方向 ④ 的 utoipa 评估**——接受 aides 替代方案
4. **方向 ① 的 Toxiproxy 建议**——接受，作为阶段 B

**但我持保留意见的一点：** 输入文档建议方向 ① 阶段 A 在 2-3 天内完成「单元级故障模拟 + 测试」。这过于乐观。`AtomicBool` 故障开关虽然简单，但需要在每个关键模块（DB、Redis、NATS、BlobStore）添加 + 覆盖所有 error path 的测试。实际估算应为 5 天。

---

## 结语

Aero IM 的架构基础是扎实的——事件驱动骨架 + 进程内扇出的分层模式是正确的，crate 的依赖方向是健康的（自下而上无环）。156 次迁移（加上本次新增的一个）虽然零回滚是技术债，但因迁移粒度小（多数为单表创建），逆向工程的成本低于预期。

五条方向中，**方向 ⑤（Schema 演化安全管线）是最应该优先执行的**——不是因为它最紧急，而是因为它是其他方向的使能器。安全的迁移管线意味着方向 ③ 的核对框架、方向 ② 的审计事件、方向 ④ 的 API 平台都可以在不担心 DDL 事故的前提下进行。
