# Aero IM 架构分析

## 1. 架构评估

### 1.1 当前架构的优势

**分层严格 — crate 即为领域边界。** 项目遵循"一 crate 一职责"原则，形成了清晰的依赖拓扑（common → bus/storage/auth → im-core/live-core → server）。我已验证 17 个 crate 之间没有循环依赖，`aero-common` 确实是一个叶子节点（无内部依赖）。这一基础使得团队无需重大重构即可处理多个独立工作流。

**事件总线是适当的基础设施基元。** 在 NATS JetStream 上选择 `per-subject 单调 seq` + `durable consumer` 作为跨实例扇出的事实依据，是有先见之明的决定。序列化成本仅为 JSON → `Arc<String>` → 共享引用。`hub.rs` 经过验证，通过 `DashMap<ParticipantId, Vec<WsSender>>` 实现了本进程 O(N) per-participant 扇出，而非 O(R) per-room（R = 房间数量），还包括：
- **lossy 标志 + resync 帧**：用于丢弃慢消费者，并让客户端通过 REST 回退进行自我修复
- **并行扇出**：注释表明 >100 个接收方会走线程池
- **双模式背压**：`disconnect_on_full`（踢出）或 `drop-only`（保留连接但丢弃帧）

**AI 管线遵循 fail-open 原则且具备预算意识。** `AiWorker` 通过 `FOR UPDATE SKIP LOCKED` + `Semaphore` 并发限制 + 加权预算（Embed=1, Moderate=2, Summarize=3, Answer=5）+ dead-letter after 5 attempts 来轮询 PG `ai_jobs`。每个机器人（agent_bot、transcribe_bot、unfurl_bot 等）都是独立的 NATS consumer，并具有防御性门控：自锁、幂等守卫、fail-open 日志记录跳过，而非出现错误时崩溃。

**Web 前端有意保持简约。** 约 1009 行的 `app.js`，零前端框架，独立模块文件，打包 CDN 依赖（hls.js、RTCPeerConnection）。这是一种经过深思熟虑的成本策略：后端是差异化优势所在，而在浏览器中渲染消息列表所需的功能则保持精简。

### 1.2 局限性

**功能边界与 UI 边界之间存在巨大缺口。** 当前状态：

| 后端能力 | 前端 UI | 差距 |
|---|---|---|
| 通知聚合 + 重要性评分 + 打包 | 141 行 notifications.js（徽章 + 列表 + 全部已读） | 缺失：分组、严重性颜色、操作、批量操作 |
| 管理面板（审计、会话、webhook、2FA、法律保留、信息屏障、组织架构图） | 零 UI | 完全空白 |
| 文件索引（名称/类型/大小） | 基本文件列表 | 缺失：全文文件内容搜索 |
| 高级搜索（操作符、混合向量、保存的搜索） | `search.js` | 存在但搜索建议/拼写修正未连接 |
| 频道/工作区配置（角色、保留、安全） | 零 UI | 完全空白 |

这并不是代码库的失败——后端已经成熟，但**前端与服务端能力的比例严重失衡**。对于面向企业的产品而言，这是一个问题：IM 聊天可以靠基本的 WebSocket 帧生存，但管理后端、合规、搜索和通知配置是管理员要求提供的功能。

**WebSocket 协议缺少版本控制和演进策略。** WS 帧在 `ws/ws_impl/` 中定义为 `ClientFrame` / `ServerFrame` 枚举，没有版本前缀、兼容性填充或协商机制。目前这还行，因为只有一个 Web 客户端和一个后端，但随着移动端 SDK 或第三方集成的加入，没有演进策略的严格 typed 枚举将成为障碍。

**hub.rs 的背压逻辑虽然先进，但未在指标中暴露。** `lossy` 标志被合适地设置和清除，resync 帧被发送——但丢弃帧总数、lossy 连接数、lossy 事件总持续时间**均未在 Prometheus 中暴露**。在运营层面，你无法知道正在发生丢帧，除非客户端抱怨消息丢失。

**迁移嵌入二进制文件是正确选择，但构建流程存在陷阱。** AGENTS.md §4.2 正确描述了这一点：`sqlx::migrate!("../../migrations")` 在编译时嵌入迁移。但 `cargo build` 然后 `aero-cli migrate` 的要求使得 CI 流水线出错成本较高——忘记重新构建就直接重新迁移会导致静默无操作，且无需硬性检查。更严格的构建系统集成（在二进制文件上做构建时间戳检查与数据库迁移版本）可以将此类错误转化为硬性故障。

### 1.3 架构债务

**1. `aero-storage/lib.rs` 中的重导出冲突** — AGENTS.md §4.2 正确记录了存在重名帮助函数（`generate_token`、`hash_token`），这些函数分布在 `webhook`、`scim`、`invitation` 中。当前约定（仅 `webhook` 重新导出到根路径，其他使用子路径）笨拙但可维护。正式名称空间限定（例如 `pub mod helpers { pub use webhook::{generate_token, hash_token}; }`）会更清晰。

**2. 通话语义的行级状态机缺失。** `CallOrchestrator` 处理 1:1 和群组通话编排，但缺乏像消息投递那样的正式幂等状态图（at-least-once + 幂等键 + dead-letter）。通话 `start`/`answer`/`end` 流程有竞争条件：两个参与者同时接听，或一方在网络分区中挂断然后立即重新通话。目前没有幂等键来防止重复的通话记录。

**3. 管理端点缺少统一鉴权层。** 每个管理路由都独立检查 `member_role(Owner/Admin)`。这对于避免跨会话权限升级（IDOR，AGENTS.md 中已记录）来说是正确的，但缺乏声明式中间件意味着新的管理路由很容易忘记检查（CI `authz_lint` 可以捕捉，但通过在路由注册时强制类型化的 `AdminRoute<F>` 包装器来消除整个漏洞类别会更好）。

**4. Rust 代码和迁移计数之间存在隐含耦合。** 代码库引用了假设存在的表或列（例如，webhook 或通知存储库中的 SQL 查询），但并未对照迁移清单进行静态验证。`sqlx::query!` 宏将在编译时捕获错位的列，但项目使用 `sqlx::query(...).bind(...)`（运行时字符串），这意味着某些列/表不匹配仅在运行时才会显现。这使得重构迁移变得有风险——你可能会更改迁移，但直到部署到 staging 环境后才会发现生产代码中的查询。

## 2. 扩展方向

### 方向 A：文件内容搜索（P1 — 知识管理差异化优势）

**为什么需要：** 团队协作平台的核心命题是"组织知识"。Slack、Teams 和 Notion 都在文件内容搜索上投入了巨资。Aero IM 已经拥有 pgvector 和 FTS 基础设施用于消息搜索——将相同能力扩展到文件内容是一个自然的扩展，可在知识管理方面创造显著的产品差异化优势。

**核心挑战：**
- **摄取管道**：上传的文件（`BlobStore`）是纯字节——PDF、DOCX、图像中的文本，都需要提取。目前没有异步文档文本提取队列。
- **存储**：现有 `blobs` 表没有 `text_content` 列。添加一个 `text_content TEXT` 列（可选，可为空，延迟加载）是最小变更路径。
- **搜索路由**：文件搜索需要一个新的搜索混合体——跨文件元数据（名称/类型/所有者）和文件内容进行搜索，并像消息搜索一样限定在房间/工作区范围内。
- **OCR 与非文本文件**：图像需要 OCR 管道；音频文件需要转录。这增加了复杂度，但遵循与 `transcribe_bot` 相同的事件驱动模式。

**架构变更：**
- 新的仓储层：`FileContentRepo`，放在 `aero-storage/src/file_content.rs`。
- 新的 AI worker 作业类型：`AiJobKind::ExtractText`，加权 2（中等复杂度）。
- 新的 NATS 主题或直接排队：`blob.text_extract`，由接收到 `BlobStore::finalize` 事件驱动。
- 扩展后的搜索路由 `POST /api/rooms/:id/files/search`，返回文件级结果（不仅仅是消息级）。

**对现有系统的影响：** 影响较小。`BlobRepo` 不变。添加新表、新 worker 作业类型和搜索路由。对现有消息搜索的查询路径无影响。

### 方向 B：管理控制台（P1 — 企业准入门槛）

**为什么需要：** 当前后端已具备审计日志、会话管理、2FA 强制执行、法律保留、信息屏障、频道保留策略、Webhook 管理、组织架构图、频道角色等完整能力。一个企业买家在购买前会要求**看到**这些管理屏幕。没有 UI 意味着每个管理功能都需要 API 调用，这会阻止自助式采用。

**核心挑战：**
- **范围**：从审计日志查看器到角色管理，涉及 15 个以上的管理屏幕。更明智的做法是建立一个"模块化"管理 SPA，将所有管理功能优雅地代理到现有的 REST API。
- **鉴权**：管理 UI 必须遵守与 API 层相同的 RBAC 边界——不同的管理员视图取决于他们是工作区管理员、全局管理员还是频道管理员。前端不应仅仅因为某个端点存在就暴露它。
- **工作量**：管理 UI 的代码体积可能**超过**主应用 UI。这需要一种有条理的方法来防止"全有或全无"的发布。

**架构变更：**
- 前端新增 `admin/` 目录，采用与主 SPA 相同的无框架模式（最小化工具链依赖）。
- 后端新增 `GET /api/admin/menu` 路由，返回当前用户的管理权限（即他们可以查看哪些管理部分），以动态驱动管理侧边栏。
- 无后端架构变更——所有数据已经流入现有 API。

**对现有系统的影响：** 完全隔离。新前端文件，新路由。所有现有 API 保持不兼容。

### 方向 C：通知 UX 全面升级（P1 — 每日触达频率最高）

**为什么需要：** 通知是 IM 平台中交互最频繁的 UI 表面——用户每天接收数十到数百条通知。后端已经就位：打包（migration 0143）、重要性评分（migration 0139，DB 列 `n`，Rust 字段 `importance_score`）、聚合（migration 0138）。但用户看到的只是 141 行的 `notifications.js`：未读计数 + 纯文本列表 + 全部已读。通知分类、严重性颜色代码、操作（静音、归档、点击跳转）、批量选择以及按优先级排序的功能全部缺失。

**核心挑战：**
- **绑定后端信号**：`notification_bundles` 表存在于后端，但前端完全不使用。需要连接 WebSocket 帧（或 REST 端点），以便前端可以实时渲染聚合通知组。
- **重要性信号**：重要性评分（DB 中的 `n REAL`）可以被前端用来进行视觉优先级排序——关键提及显示为红色，低优先级回复显示为灰色。目前完全未使用。
- **操作**：前端需要批量操作（全部标记为已读、选择多个并归档、静音某人的线程），这些操作确实有后端端点（`read_all`、`mark_unread`），但 UI 中没有暴露。

**架构变更：**
- 前端：`notifications.js` 重写为 ~400-500 行。新徽章组件增加动画效果。
- 后端：新增 `PATCH /api/notifications/batch`（目前仅逐一操作）。新增 `GET /api/notifications?include_bundles=true` 返回分组数据。次要变更。

**对现有系统的影响：** 影响较小。仅新增前端代码和少数补充后端路由。所有现有通知端点保持向后兼容。

### 方向 D：WebSocket 协议演进（P2 — 长期可维护性）

**为什么需要：** 目前，WebSocket 帧是紧密耦合的 Rust 枚举 ↔ JavaScript switch 语句。没有版本控制、兼容性垫片或面向未来的机制。随着移动端 SDK（最终）、第三方集成或仅仅是更复杂的 Web 客户端的出现，WS 帧格式将成为耦合最紧密的集成点。正确定义这一点可以防止未来发生断裂式变更。

**核心挑战：**
- **向后兼容性**：服务器和客户端通常同时部署，但并非总是如此（滚动重启、金丝雀部署）。帧格式应允许服务器添加可选字段，而客户端无需中断即可忽略这些字段。
- **连接协商**：是否在 WS 升级期间进行协议版本协商？是否使用 `Sec-WebSocket-Protocol`？是否在初始帧中发送简单的 `{ "v": 1 }`？每种方式都有权衡。
- **迁移**：放宽严格 typed 枚举以允许"额外字段"可能会引入 bug，因为拼写错误的字段名将静默通过验证。

**架构变更：**
- `common/src/model/ws.rs`：引入 `FrameVersion` 枚举 + 带有可选 `version` 字段的 `ClientHello` 帧。
- `ws/ws_impl/`：在 server frame 枚举中添加向前兼容的 `#[serde(deny_unknown_fields)]`，但 client frame 需要 `#[serde(deny_unknown_fields)]`（因此拼写错误是硬性错误，不会静默产生无操作指令）。
- 前端：为未知帧类型添加通用的 `ws.on('msg:unknown', ...)` 处理程序。

**对现有系统的影响：** 影响中等。约 3 个文件会发生变化，涉及多个开发人员的协调。如果客户端发送旧帧风格，服务器接受该帧但不理解 `version` 字段，则可以实现向后兼容性。

### 方向 E：通话编排幂等状态机（P2 — 可靠通话体验）

**为什么需要：** 通过事件进行 1:1 和群组通话编排是容错的最后主要领域。消息传递具有 at-least-once + 幂等键 + dead-letter。通话流程具有 `start` → `answer` → `end`，但缺乏幂等键，存在竞争条件（双方同时接听，一方在网络分区中挂断然后重新接入）。由于通话延迟不可接受，严格的一次性交付过于昂贵——但错过通话记录或创建重复通话都是不好的结果。

**核心挑战：**
- **定义幂等性**：通话的"幂等键"是什么？呼叫方 + 被叫方 + 通话开始时间？呼叫方 + 被叫方 + 通话序号？在通话建立后，通话中事件的幂等性与消息不同。
- **竞争与分区恢复**：如果 `CallOrchestrator` 在写入通话记录后但在应答前崩溃，会发生什么？恢复过程必须清理孤立的通话记录，同时不删除合法的通话。
- **SFU 副作用**：SFU peer 注册在 `aero-live-webrtc` 的 `SfuRouter` 中——这是一个与通话编排器分开的进程内 `Arc<RwLock<HashMap>>`。如果 Rust 的通话记录确认了通话，但 SFU 的路由器因崩溃而丢失了 peer，通话将无声地失败。

**架构变更：**
- 在 `aero-im-call` 中引入 `CallIdempotencyKey` 类型 + `call_requests` 表（类似于 webhook 交付幂等日志）。
- `CallOrchestrator` 中的两阶段模式：阶段 1 = 使用幂等键记录意图；阶段 2 = 执行 SFU 注册。恢复扫描阶段 1 中时间过长的条目。
- SfuRouter 崩溃报告：`aero-live-webrtc` 暴露一个 `GET /internal/debug/router`，用于外部监控，以验证 SFU 状态与通话记录是否一致。

**对现有系统的影响：** 影响中等。`aero-im-call` 中新增提取 + 存储库。`aero-live-webrtc` 中新增内部调试路由。现有通话流程在新增幂等键检查之前保持不变，因此不会出现回归。

## 3. 接口设计建议

### 3.1 核心原则

**对 WS 帧使用严格的向后兼容性策略。** 目前的 `#[serde(deny_unknown_fields)]` 对于客户端输入来说是正确的（它避免了"静默忽略 typo 导致无操作"的 bug 类别）。对于服务器输出，考虑迁移到较为宽松的模式——添加字段（例如 `notification_importance`、`resync` 帧字段或 `call_kind`），这些字段对于新客户端有意义，但旧客户端如果不理解就会忽略。这会为金丝雀部署制造一个"始终安全的旧客户端"窗口。

**为 WS 帧添加版本前缀。** 一个简单的惯例，例如每个帧对象中的 `"v": 1`，允许未来版本的协议基于每个连接进行协商。切换枚举逻辑很简单：

```rust
// 概念
match frame.v {
    1 => handle_v1(frame),
    2 => handle_v2(frame), // 新字段
    _ => Err(ProtocolError::UnsupportedVersion),
}
```

这在前期是一个极小的成本（每个帧加 3 个字节），但从长远来看带来了很大的灵活性。

**为新特性和新的 WebSocket 事件使用一致的订阅模式。** 对于每个新的实时功能（文件搜索进度、AI 审核结果、通话字幕），遵循此模式：
1. 向 `RoomEvent` / `StreamEvent` 枚举添加变体
2. 向 `Hub` 添加一个扇出方法（如果接收模式是新的）
3. 向 `ws.js` 添加一个 `on('msg:...')` 处理程序
4. 在 Rust 中记录未知事件（因此不存在静默丢失新帧的情况）

### 3.2 新的抽象层

**事件序列化和帧序列化之间需要分离。** 目前，`RoomEvent`（领域事件）在总线序列化中直接是 JSON，然后由 `run_bus_listener` 解析，并作为 `ServerFrame` 重新序列化。这创建了一个隐式耦合：领域事件中的每个字段都成为 WS 帧的一部分。当内部领域事件发生变化时，WS 协议会发生断裂式变化。明确的 `ServerFrame::Event(RoomEvent)` → `ServerFrame::to_json()` 映射会更安全，但会增加序列化成本。

**引入 `FanOutStrategy` 枚举**，可优化 hub 扇出。目前，hub.rs 对所有事件使用统一的 `fan_out_raw`。作为方向 D（协议演进）的一部分，引入：

```rust
pub enum FanOutStrategy {
    /// 发送给房间里每个人（消息、已编辑、已删除）
    All,
    /// 仅发送给活跃参与者（跳过潜伏者——打字中、已读回执）
    ActiveOnly,
    /// 仅发送给显式列出的接收者（通知、提及）
    Recipients(Vec<ParticipantId>),
    /// 发送给有音频栏且至少有一个参与者订阅的连接（通话）
    CallParticipants(CallId),
}
```

这会将扇出逻辑的类型安全边界从 human convention 提升到编译器强制。它在 hub.rs 中为大约 20 行新代码。

### 3.3 向后兼容性策略

**WS 帧：逐步添加字段，避免标为必需。** 新字段使用 `#[serde(default)]` 或 `Option` 修饰。客户端使用 `obj.newField ?? fallback` 模式。通过正确的行为，一个金丝雀后端可以与生产前端一起工作。

**REST API：使用 `Accept` 和 `Content-Type` 进行版本控制。** 项目目前不使用这些头信息（API 默认使用 `application/json`）。添加一个 `application/vnd.aero.v1+json` 内容类型作为偏好，同时保持 `application/json` 作为 v1 的后备。允许将未来的断裂式变更放在 v2 媒体类型后面。

**迁移：对具有组织影响的列使用保守的模式变更。** `NOT NULL` 的新列应具有默认值或分两步部署：步骤 1 = 添加可为空的列，填充数据；步骤 2 = 添加 `NOT NULL` 约束。查询应在列存在时使用 `COALESCE`，以处理在 rollout 期间遇到任一模式的任何进程。

## 4. 技术选型

### 4.1 评估新依赖项的框架

任何新的第三方 crate 都应满足以下条件：

| 条件 | 为什么 |
|---|---|
| 在 crates.io 上至少有 6 个月的积极维护 | 防止通过废弃的依赖项引入供应链风险 |
| 当前的 MSRV 不晚于我们的 MSRV（1.80）超过一个版本 | 避免 Rust 升级级联 |
| `#![forbid(unsafe_code)]` 或安全使用 unsafe 的有据可查的极少数情况 | 符合项目 `unsafe_code = "forbid"` 的 lint |
| 使用 tokio 的异步接口（对于 I/O 型 crate） | 避免线程池分裂 |
| 纯 Rust 首选；经过审核的 C 绑定可以接受 | 保持交叉编译简单 |

### 4.2 建议的补充

| 依赖项 | 替换什么 | 论据 |
|---|---|---|
| **`tantivy`**（带安全的 Rust 包装器） | 当前 pg_trgm FTS | 用于文件内容搜索的专用全文搜索索引比 PG 的基于行的扫描更快。但这与 `pgvector` 正交，PG 的 pgvector 仍然可以进行语义搜索。**不建议替代**，仅作为文件索引的附加组件。 |
| **`lopdf`** 或 **`pdf-extract`** | PDF 文本提取（当前不存在） | 文档文本提取管道的必备条件。纯 Rust 中的 PDF 提取是可行的。对于 DOCX，解析 ZIP 中的 XML 很简单，无需 crate。 |
| **`quickjs`** 或 **`boa_engine`** | 无（当前不使用） | 如果管理控制台中的工作流自动化成为目标（例如，类似 Slack 的工作流构建器），那么在 Rust 中嵌入 JS 沙箱是有意义的。目前还不成熟，但值得关注。 |
| **`opentelemetry-proto`** | 当前的 OTLP 导出是手动完成的 | 如果 OTLP 成为主要的可观测性出口，则值得进行标准化。目前 Prometheus 端点只需最少的 crate 支持即可正常运行。 |

### 4.3 自建 vs. 采购决策

**自建：文件文本提取器。** 与消息嵌入 pipeline（`embedding_backfill` 计时器 - `AiWorker` - PG）架构相同的天然候选项。模式相同：`BlobStore.finalize` 事件 → NATS → `extract_text_bot` → `AiJobKind::ExtractText` → worker → 行更新。没有现成的 crate 能提供这种编排。

**采购（慎重）：用于高级搜索的专门搜索引擎。** 如果文件内容搜索规模很大（每个工作区超过 100 万个文件），PG 的全文搜索 + trigram 可能不足以胜任。此时可以使用 Elasticsearch 或 MeiliSearch，但将其保留为**建议**，而不是硬性要求。Aero 的 PG 当前实现（`pgvector` + `pg_trgm` + `search_tsv` GIN 索引）设计良好，应该可以扩展到相当大的规模。

**不采购：AI 推理基础设施。** Anthropic API 网关（当前使用 Anthropic Messages API）将 AI 复杂性保持在外部。切换到自托管 LLM 将是成本驱动而非功能驱动，应该推迟到规模需要时。

## 5. 实施路线图

### 阶段 0：基础工具（2 周）

此阶段不对用户施加任何影响，但为所有后续工作提供了基础。

| 项目 | 工作 | 风险 |
|---|---|---|
| WS 帧中添加版本前缀 | 每个未来帧格式变更都会得到一个 "v"。向 ws.js 添加 `v` 处理。 | 低。向所有帧添加 3 个字节。没有用户可见的变化。 |
| Hub 指标暴露 | 暴露 `ws_frames_dropped_total`、`ws_lossy_connections`、`ws_lossy_duration_seconds`。在 Grafana 中创建仪表盘。 | 低。仅指标。无逻辑变更。 |
| 通话编排幂等键 | 添加 `call_requests` 表 + 幂等键检查。为长时间运行的意图添加恢复逻辑。 | 中等。新表，对 start/answer 流程的变更。测试关键。 |
| 文件索引 extension（元数据） | 如果尚未添加，添加 `file_index.text_content` 列到迁移中。添加空提取器桩。 | 低。新列，默认 null。无摄取触发。 |

### 阶段 1：高触达频率、低风险（3-4 周）

在不对后端进行重大更改的情况下，通过改善目前最薄弱的 UI 来提供最大的早期用户价值。

| 项目 | 工作 | 依赖项 |
|---|---|---|
| **通知 UX 升级** | 重写 `notifications.js`（400-500 行）。添加重要性指示器（颜色编码）、分组摘要、按 bundle 类型筛选、批量操作选择。 | 阶段 0 WS 帧版本 |
| 批量通知操作 | `PATCH /api/notifications/batch`（基于 ID 数组的标记已读/归档/静音）。 | 通知 UX 升级 |
| 通知 bundle 端点 | `GET /api/notifications?bundled=true`，按 `notification_bundles` 表的 bundle ID 对通知进行分组。 | 通知 UX 升级 |
| `prompt()` 编辑替换为内联编辑 | 将 `app.js:779` 中的 `prompt('编辑消息:', text)` 替换为适当的内联输入字段。约 30 行变更。 | 无 |

**风险**：通知重写会破坏现有的徽章计数逻辑？不——徽章计数在 Rust 端由 Hub unsubscribe 处理。前端仅使用 WebSocket 帧。重写是纯前端变更。

### 阶段 2：文件内容搜索（4-5 周）

| 项目 | 工作 | 依赖项 |
|---|---|---|
| 文件文本提取 pipeline | 新 worker 作业类型 + `extract_text_bot` + PDF/DOCX/图像提取器（前两个月使用基础的 `pdftotext`，然后进行优化）。 | 阶段 0：file_index text_content 列 |
| 文件内容搜索路由 | `POST /api/rooms/:id/files/search` 对 `blobs.text_content` 进行 FTS + trigram 混合搜索，并进行房间作用域限制。 | 文件文本提取 pipeline |
| 前端：文件搜索结果 | 新的 UI 组件，显示文件名 + 片段 + 匹配高亮。复用现有的 `search.js` 模式。 | 文件内容搜索路由 |
| 文件搜索输入时建议 | 当用户在工作区搜索框中输入时，交叉引用文件名。 | 文件内容搜索路由 |

**风险**：文本提取在 1 秒内无法完成的慢速文件可能阻塞 worker 线程。通过在 worker 中使用 `tokio::task::spawn_blocking` 并将提取超时设为可配置（默认 30 秒）来缓解。

### 阶段 3：管理控制台（6-8 周）

| 项目 | 工作 | 注释 |
|---|---|---|
| 管理 SPA 脚手架 | 新的 `web/admin/` 目录，使用无框架的 SPA 模式。从 `GET /api/admin/menu` 驱动侧边栏。 | 与主 SPA 相同的设计系统。 |
| 核心管理屏幕 | 审计日志查看器、会话管理、2FA 状态、webhook 管理、法律保留列表。约 5 个屏幕。 | 核心企业准入要求。 |
| 扩展管理屏幕 | 组织架构图、信息屏障、频道保留、角色管理、公告。约 5 个屏幕。 | 配置复杂度更高；由版本支持。 |
| 管理通知 | 与主通知系统集成的管理内告警（例如，"webhook 交付失败"）。 | 新功能，而非现有功能的复刻。 |

**风险**：15 个管理屏幕在 6 周内对单个或多个开发人员来说是一个很大的工作量。建议采用模块化方法：在 Phase 3a 中交付审计 + 会话 + webhook，在 Phase 3b 中交付其余部分，中间间隔至少 2 周。

### 阶段 4：高级搜索 + AI 愿景（4-6 周）

| 项目 | 工作 | 注释 |
|---|---|---|
| 搜索操作符 UI | 前端搜索框工具提示显示 `from:`、`in:`、`before:`、`after:` 语法。自动完成这些操作符。 | 完成后端到目前为止未使用的 `parse_search_query` 管道。 |
| 保存的搜索 UI | 使 "保存搜索" 按钮真正起作用。列出已保存的搜索，重新运行，删除。 | 连接到现有的 `SavedSearchRepo`。 |
| AI 驱动的搜索建议 | 当用户键入时，使用 `/ask/stream` 获取搜索建议。 | 需要 Anthropic 连接；需要 graceful 退化。 |
| AI 跨房间用户画像 | 启用 `AERO_AI_CROSS_ROOM_PROFILE`——从跨房间的公共消息构建用户画像。 | 与 AI 管道正交的后端开关。 |

### 优先级总结

```
Stage 0 (工具)     → P0 — 为所有后续工作提供基础
Stage 1 (通知)     → P1 — 最高用户触达频率；后端已就位；3-4 周
Stage 2 (文件搜索) → P1 — 知识管理差异化优势；4-5 周
Stage 3 (管理)     → P1 — 企业准入要求；6-8 周  
Stage 4 (高级搜索) → P2 — 用户反馈驱动；4-6 周
```

### 关键风险与缓解措施

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| **管理控制台范围蔓延** | 高 | 高（6 周的阶段可能变成 12） | 预先硬性定义 "核心"（审计、会话、webhook、2FA）vs "扩展"（所有其他内容）。当核心可用时再发布。 |
| **文件文本提取性能瓶颈** | 中 | 中（worker 队列积压） | 使用 `tokio::task::spawn_blocking`；默认限制并发提取为 2。添加提取每文件超时（30 秒）。 |
| **WS 帧版本化导致兼容性复杂** | 低 | 低（没有其他客户端） | 阶段 0 引入版本化；重写所有现有帧以包含 `"v": 1`。没有行为变更。 |
| **通知重写破坏现有徽章** | 低 | 高（用户可见） | 保留现有的 `unread_count` 端点不变。在切换过程中与新 UI 并行测试。 |
| **SFU/call-bridge seam 产生级联失败** | 中 | 高（通话声音中断） | 在切入生产环境之前，*严格*进行阶段 0 幂等升级 + 为 SFU 路由器添加崩溃报告端点。 |
