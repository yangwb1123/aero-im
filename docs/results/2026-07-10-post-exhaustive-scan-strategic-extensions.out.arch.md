## 3. 我的建议：P0 方向选择与优先级排序

### 标准

| 维度 | 权重 | 说明 |
|------|------|------|
| 用户可见 | 高 | 不写一行 UI 的功能等于不存在 |
| 交付风险 | 中 | 避免需要 3+ 个月才能见到效果的方向 |
| 依赖关系 | 高 | 优先解除阻塞后续方向的瓶颈 |
| 竞品差异 | 中 | AI-Native + 直播是核心差异化，但基础体验不能有硬伤 |
| 维护成本 | 低 | 当前架构已运营的隐形成本 |

### P0（立即开始）

#### 1. Web SPA 产品化 —— 第一阶段：文件上传 + 消息体验

**为什么选上传作为起点，而非更大范围的 Admin Console？**
- 上传是每个用户、每天、每次使用的功能。当前「盲传」体验是最大的 UX 负资产
- 后端管线已完备（S3 / AV 扫描 / 内容嗅探 / 转写）——只缺前端
- 估算体量小（L1 ~5 天），可在第一周交付可见改善
- 不影响现有架构，纯前端变更 + 1 个 REST API

**为什么不选 Admin Console？**
- Admin Console 需要定义企业级 UI 框架选型（React/Vue？组件库？），决策成本高
- 涉及的工作区/频道/用户管理 API 当前零前端覆盖，起步就是 4-6 周
- Admin Console 的受益者是管理员（少数人），上传的受益者是所有用户

**第一阶段任务（按顺序）**：
1. `api.js` 中 `uploadBlob` 从 `fetch` 改为 `XMLHttpRequest` + `onprogress` → 进度回调
2. `media.js` 增加上传进度条 DOM 渲染 + `AbortController` 取消
3. 拖拽视觉区域（全屏遮罩 + 文件类型图标）
4. 上传前预览（composer 上方缩略图 + 文件名 + 大小 + 确认/取消）
5. 前端校验 MIME 白名单 + 32MB 上限（服务端已有，前端提早拒绝）
6. 后端 `GET /api/me/storage` → 前端用量仪表盘（为后续配额定价铺路）

**第二阶段：消息 Composer 增强**
- 富文本输入（`contenteditable` → 有限 markdown 快捷渲染）
- 草稿持久化（`localStorage` + 切换房间恢复）
- 斜杠命令面板（`/giphy`, `/poll`, `/code` 等）

#### 2. 进程生命周期管理 —— 启动/关闭窗口期事件静默丢失 (P1 · 可靠性)

**为什么 P0？** 372 份分析中唯一一份**零覆盖**的 P1 架构缺陷。当前启动时序中：

```
build_state()       → Hub 零连接
spawn_background()  → bus listener 开始消费（NATS 光标推进）
serve()             → HTTP 开始接受 WS 连接
```

这之间有 ~50ms-500ms（取决于启动复杂度）的窗口期，事件被消费但无 WS 扇出目标。在生产环境多实例滚动部署时，每次重启都会系统性丢失事件。

**修复方案**（仅后端，无需前端）：
1. 给 `run_bus_listener` / `run_live_bus_listener` 增加启动门控：一个 `watch::Receiver<bool>` 初始为 `false`，直到 `serve()` 开始接受 WS 连接且第一条 WS 连接注册后才设为 `true`
2. 关闭时反向：先关闭 `watch` 信道 → 停止消费新事件 → drain 已消费但未扇出的事件 → 关闭 HTTP → 关闭后台任务
3. 为 `tracker.spawn` 的所有后台任务增加 `cancel_token` 参数

**体量**：纯后端，~3 个文件修改（`main.rs` / `background.rs` / `serve.rs`），~2 天。

### P1（下一批）

#### 3. 多实例限流失配

**问题**：HTTP 限流器和登录限流器是 in-process `HashMap`。N 节点下实际限流阈值 = N × 配置值。攻击者跨节点分散请求即可绕过。

**为什么不是 P0？**
- 当前无公开部署，不在攻击面
- 修复需要引入 Redis 分布式计数器（`INCR` + `EXPIRE`），增加基础设施依赖和延迟
- 现有的 `AERO_RATE_LIMIT_PER_SEC` 在单节点开发环境完全可用

**修复方案**（选择 A 或 B）：
- **方案 A（轻量）**：在限流 key 中加入 `hostname` 后缀，使每节点独立限流（不解决分布式绕过，但防止节点间共享计数器导致的非预期行为）。~1 天。
- **方案 B（完整）**：`fred` 已有 Redis 连接，限流器改用 `RedisRateLimiter`（滑动窗口 + `INCR` + `EXPIRE`）。给现有限流 trait 加一个 Redis 实现。~3 天。

**建议**：选方案 A 做短期防护，方案 B 标记为「待 Redis 连接池压力测试后实施」。

#### 4. 软删消息的寄生物表孤儿数据

**问题**：消息软删后，`reactions` / `receipts` / `pins` / `interactions` 等表关联行永久残留。

**修复方案**：
- 在 `soft_delete_audited` 的事务体中增加 `DELETE FROM reactions WHERE message_id = $1` 等级联删除
- 当前事务已锁行，增加 DELETE 语句无额外事务开销
- ~4 个仓储方法扩展，~1 天

### P2（远期/战略储备）

#### 5. 大规模房间投递写放大控制

**挑战**：10 万人房间每消息 O(N) 展开 + 通知 + 推送。当前架构的上限清晰可计算。

**为什么不是 P0？**
- 产品当前没有 10 万人房间的客户
- 修复涉及 Hub 架构变更（懒惰扇出 / 分页展开 / 在线子集广播），是核心架构改动
- 需要先有压测数据确定瓶颈阈值，而非过早优化

**建议动作**：
- 在总线 listener 路径上增加 `room_size` 指标仪表盘，持续监控
- 当 max(room_size) 超过 5,000 时触发对应优化

#### 6. MLS E2E 加密

**战略价值高但工程成本极高**：需要 openmls-wasm、客户端密钥管理、解密代理架构、法务保全冲突设计。当前业务阶段（单租户、非金融/医疗）下 ROI 不足。**标记为「24 个月路线图」**。
