# 架构分析：当分析本身成为架构债务

## 1. 架构评估

### 1.1 当前架构的优势

这个代码库在技术架构层面表现出高度的成熟度。crate 分层清晰（基础层→IM 层→直播层→组合层），依赖方向自下而上无环，事件总线基于 NATS JetStream 的设计为跨实例水平扩展提供了坚实基础。路由模块化程度高——126 个 `.merge()` 调用意味着每个能力域有独立的 route 模块，这是从单体快速演化时保持组织性的良好实践。

Rust 技术栈的选择（sqlx、str0m、tokio）也与问题域高度匹配：直播串流的实时性要求、WebRTC 的零分配路径、IM 消息的持久化事务，这些在 GC 语言中会更难控制。

### 1.2 但：代码库的「架构剖面」存在严重偏斜

| 维度 | 后端 (Rust) | 前端 (Web SPA) | 分析文档 |
|------|------------|----------------|---------|
| 代码量 | ~143,224 行 | ~4,318 行 | ~102,000 行 |
| 测试 | ~505 个 | 0 个 | 验证报告附带，但未集成到 CI |
| 模块数 | 126+ 路由模块 | 18 个 JS 文件 | 395 份文档 |
| 技术债务管理 | 有 HARNESS.md 门控 | 无门控 | 无门控 |

**这是一个头重脚轻的架构：后端工程化程度很高，但前端仍停留在「debug client」阶段，而分析文档的膨胀已经超过前端代码量的 23 倍。**

### 1.3 关键设计决策的合理性

- **NATS JetStream 作为跨实例事实源**：合理。Durable consumer 加 per-subject seq 的架构使 at-least-once 投递和客户端去重变得清晰。但 `run_live_bus_listener` 使用 ephemeral consumer 意味着重启时丢失的弹幕没有重放保障——这在当前 scale 下是可接受的 tradeoff，但文档中对此的讨论量（27 次提及）远超过了所需的工程投入（一次参数调整）。

- **Redis sorted-set 作为集群状态**：合理。Presence、viewer count、call roster 这些有 TTL 的短暂状态天然适合 Redis，避免每次读取穿透到 PG。Redis 故障时的 fail-open 策略也是务实的。

- **SFU 的进程内 `SfuRouter`（`Arc<RwLock<HashMap>>`）而非 Redis**：短期合理。在单节点部署中，进程内 HashMap 比 Redis 往返快一个数量级。但长期来看，当需要跨节点 SFU 媒体面路由时，这个设计会成为障碍——而 `call_bridge_supervisor` 和 `SfuForwarder` 正是为此而建但「生产未接线」。

### 1.4 关键的架构债务

**债务一：前端基础设施为零。**
`web/` 目录是一个无构建工具、无测试框架、无类型检查的零依赖 SPA。`index.html` 的标题是 `"Aero IM — Debug Client"`——这不是生产就绪的声明，而是事实。18 个 JS 文件共 4,318 行，没有模块打包器，没有 lint 集成到 CI，没有端到端测试。后端有 126 个路由模块，前端 UI 覆盖率约 20%。这意味着大量后端 API 无人消费——它们在生产中没有被验证过。

**债务二：分析过剩，实现不足。**
395 份文件、102,000 行的分析文档对应零行实现。这不是「文档驱动开发」，这是「分析替代开发」。每个分析文档本身消耗了「代码遍历→推理→写报告→验证→修正」的完整循环，而这些循环本可以直接产出代码。

**债务三：关键 seam 已建但未接线。**
`call_bridge_supervisor.rs` 和 `sfu_media_session.rs` 已编码和单元测试，但生产路径零调用。这意味着：
- 这些模块的运行时正确性未经端到端验证
- 它们的接口可能在实际接线时暴露出不匹配
- 维护它们需要持续成本（编译、依赖升级、clippy 检查），但没有运行时收益

**债务四：测试集中在 Rust 层，前端和集成测试为零。**
505 个 Rust 单元测试验证了后端逻辑，但没有一个测试验证从「用户点击发送按钮」到「消息出现在另一个用户屏幕上」的端到端路径。WebSockets、实时更新、UI 状态管理的核心链路实际上是无测试的。

## 2. 扩展方向

### 2.1 [P0] 前端基础设施化

**为什么需要**：4,318 行零测试的 JS 代码承载着整个产品的前端体验。当前架构中，前端是唯一的单点故障（SPOF）——没有它，整个产品不可用。每一个后端功能上线时，如果没有匹配的前端实现，就等于没有上线。

**核心挑战**：
- 从零构建前端工程化基础设施需要做一组技术决策（打包器、类型系统、测试框架、组件模型），每项决策都有沉没成本
- 需要在「保留现有零依赖 JS」和「迁移到现代前端框架」之间做权衡
- 前端开发者与后端 Rust 开发者的技能集不同——当前团队可能缺少前端 expertise

**架构变更**：
- 选项 A（渐进式）：引入 Vite 作为构建打包器，保留原生 JS，逐步加入 TypeScript 类型标注（`.d.ts` 或逐步 `.ts`）。测试用 Vitest + Playwright。
- 选项 B（框架迁移）：迁移到 React/Vue + TypeScript，从关键路径（消息流、通话）开始重写。
- 选项 C（混合）：现有页面保持原生 JS + Vite 构建，新功能（VOD 管理、管理后台）用 Svelte 或 Preact 构建。

**推荐**：选项 A。考虑到这是一个「debug client」升级为生产客户端的过程，渐进式迁移的风险最低。Vite 可以零配置处理现有的 `.js` 文件，TypeScript 是逐步可选的。

**对现有系统的影响**：低。前端重构不改变后端 API 契约。WebSocket 帧格式保持不变。

### 2.2 [P0] 端到端测试基础设施

**为什么需要**：当前测试只在 Rust 层。没有集成测试验证整个系统的工作——从 WS 消息投递到 Hub 扇出到前端渲染。每次部署都是对生产的一次赌博。

**核心挑战**：
- 测试环境需要启动完整的后端栈（PG、Redis、NATS、Axum server）
- WebSocket 实时测试比 REST API 测试复杂一个数量级
- 需要确定「测试什么」的边界——全量端到端 vs 关键路径

**架构变更**：
- 引入 `tests/` 目录（或当前 crate 中的 `tests/` 目录）存放集成测试
- 测试启动时用 `docker compose` 拉起依赖服务
- 对 WebSocket 路径编写 `send_message → 确认消息到达另一连接` 的场景
- CI 中运行关键路径，PR 中作为门控

**对现有系统的影响**：中。需要增加测试基础设施（docker compose 配置、测试 fixture、CI 编排），但不改变任何生产代码。

### 2.3 [P1] 接线已有的 seam：call_bridge 与 sfu_media_session

**为什么需要**：这两个模块代表了 SFU 跨节点媒体的核心能力，是系统架构中「以管道代替中心化」思维的体现。它们已建已测但未接线——这意味着要么当前架构是单节点够用（短期内可以接受），要么是开发工作未完成。AGENTS.md 中的「seam」分类表明这是有意的技术债务，但债务需要偿还计划。

**核心挑战**：
- 接线需要真对端——浏览器或配对 str0m 实例，不能在 CI 中运行
- 跨节点媒体依赖网络拓扑（UDP 端口、NAT 穿透、集群发现），比单节点复杂
- 生产接线后的维护成本（升线降线、网络分区处理、监控）

**架构变更**：
- 添加功能 flag 控制接线：`AERO_ENABLE_CALL_BRIDGE`，默认关闭
- 编写接线部署文档：需要哪些环境配置、如何验证、排障流程
- 添加集成测试（在 docker compose 中起两个实例验证 RTP 中继）

**对现有系统的影响**：低到中。代码已存在，接线是胶水层工作。

### 2.4 [P1] 工作区级数据导出（`me_export` 的车间等价物）

**为什么需要**：GDPR/数据主权要求用户可导出数据。当前 `me_export` 只支持个人 PII 导出。工作区管理员需要导出工作区数据用于迁移或合规审计。这是法律合规需求，不是功能需求。

**核心挑战**：
- 数据量：工作区可能包含数百万条消息，导出需要异步处理
- 权限边界：工作区管理员只能导出其管辖的工作区数据
- 格式标准：JSON？CSV？需要与既有 `me_export` 一致

**架构变更**：
- 新增 `WorkspaceExportRepo`，复用 `BlobStore` 存储导出结果
- 异步导出任务（现有 AiWorker 模式可复用——PG 轮询 + `SKIP LOCKED`）
- 导出任务进度通知（通过 NATS → Hub → WS → 前端）

**对现有系统的影响**：低。复用已有模式（BlobStore、异步任务队列）。

### 2.5 [P2] 停止新的分析文档，转换为实现

**为什么需要**：这不是一个技术决策，而是一个组织/流程决策。395 份 ~102,000 行的分析文档已经覆盖了代码库的每个角落。新分析文档的边际价值已经趋近于零——统计上，新的「5 个方向」几乎必然是既有方向的变体。验证报告已经重复发现了这一点。

**核心挑战**：
- 改变 Agent 行为模式需要修改 prompt 或 harness 配置
- 分析文档的生成是自动循环，需要外部干预停止
- 需要将「分析完成度」的量度从「文档数量」改为「实现覆盖率」

**架构变更**：
- 修改 `AGENTS.md` 中的流程：不再要求首先生成分析文档，而是要求先用代码填空
- 在 harness 中添加门控：如果 docs/ 中的分析文档超过代码变更量的一定比例，阻止提交
- 创建一个真正的「覆盖率追踪」文档（`COVERAGE.md`），对 routes.rs 中 126 个模块逐一标注后端实现状态、前端实现状态、测试覆盖状态

**对现有系统的影响**：无代码变更，但影响开发流程。

## 3. 接口设计建议

### 3.1 前端 - 后端接口的 X 光检查

当前前端通过两种方式与后端通信：
1. **REST API**：通过 `api.js` 封装，直接调用 Axum 路由
2. **WebSocket**：通过 `ws.js` 处理 `ServerFrame` / `ClientFrame`

**问题**：没有正式的 API 契约。REST 返回类型没有 OpenAPI 规范或 TypeScript 定义。后端改了返回值类型，前端只有运行时才能发现问题。

**建议**：
- **短期**：从 `routes.rs` 中每个路由的返回值类型生成 TypeScript 接口定义。可以用一个简单的脚本扫描 Rust 源码中的 `impl IntoResponse` 类型，输出 `.d.ts` 文件。
- **中期**：引入一个共享的类型定义文件（JSON Schema 或 protobuf），后端序列化/反序列化和前端类型检查都基于此。鉴于团队规模，JSON Schema + `schemars` crate 是最低成本方案。
- **长期**：考虑 tRPC-like 的方案，但从当前架构的 WebSocket-centric 设计来看，这不是高优先级。

### 3.2 WebSocket 帧的进化契约

当前 WebSocket 帧使用 `tag="kind"` 的 tagged enum。这是一个合理的设计——它允许 forward-compatibility（新 kind 被旧客户端忽略）。但缺乏显式的版本协商机制。

**建议**：
- 当前不需要版本协商——框架设计之初就假设了新 kind 的添加是向后兼容的
- 但需要文档化契约：`ServerFrame` 中未知 `kind` 应被忽略，`ClientFrame` 中未知 `kind` 应被忽略
- 长期：如果 WebSocket 帧格式需要 breaking change，引入连接时的 `version` 握手

### 3.3 是否需要新的抽象层

**不需要**。当前系统的抽象层已经足够：

| 层 | 抽象 | 职责 |
|---|---|---|
| 传输 | NATS JetStream | 跨实例事件投递 |
| 业务 | XService / XRepo | 业务逻辑与持久化 |
| 扇出 | Hub | 进程内 WS 扇出 |
| 媒体 | SfuRouter / SfuForwarder | SFU 媒体转发 |

当前最大的缺口不是缺少抽象层，而是**前端缺少与之对应的抽象**——前端没有一个 `XEventHandler` 模式来处理后端不断新增的 `RoomEvent` / `StreamEvent` variant。当前 `ws.js` 中处理事件的方式是分散的、事件驱动的 `if-else` 链，维护成本随后端事件类型增长而线性增加。

**建议**：在前端引入一个事件注册表模式：

```javascript
// 概念设计
class EventRouter {
  constructor() { this.handlers = new Map(); }
  on(kind, fn) { this.handlers.set(kind, fn); }
  dispatch(event) {
    const handler = this.handlers.get(event.kind) || this.handlers.get('*');
    if (handler) handler(event);
    else console.warn('Unhandled event kind:', event.kind);
  }
}
```

这不需要重写，是一个增量模式——新事件先注册，旧事件保持原样。

## 4. 技术选型

### 4.1 前端基础设施：选项对比

| 方案 | 学习成本 | 迁移成本 | 长期收益 | 推荐场景 |
|------|---------|---------|---------|---------|
| **Vite + vanilla JS** | 低 | 低（无需重写） | 中（仅构建+测试） | 短期过渡 |
| **Vite + TypeScript** | 中 | 中（逐步迁移） | 高（类型安全） | **推荐** |
| **React/Vue 框架** | 高 | 高（重写） | 高（组件生态） | 中期 |
| **Svelte** | 中 | 高（重写） | 中（体积小） | 新页面 |

**推荐**：Vite + TypeScript，逐步迁移。理由是：
- 现有 JS 文件在 Vite 中可直接运行，零配置迁移
- TypeScript 可逐步引入（`// @ts-check` JS Doc 到全量 `.ts`）
- 测试可立即使用 Vitest
- 不改变框架意味着不增加认知负担

### 4.2 第三方依赖评估

**不需要引入新的运行时依赖**。当前的 Rust 技术栈（tokio、axum、sqlx、fred、async-nats、str0m）覆盖了所有核心需求。前端如果引入框架，应遵循以下标准：

1. **树摇友好**：只打包实际使用的代码
2. **零运行时（或极小）**：保持 SPA 轻量，当前 ~4.3K 的无框架 JS 是优点而非缺点
3. **渐进式采用**：不强制一次性重写
4. **长期维护活跃**：社区要有保障

### 4.3 自建 vs 采购

当前系统几乎没有「采购」项——它本质上是自建一切。这是一个合理的决策，因为：
- IM/直播/通话是核心产品差异化所在，不是通用基础设施
- Rust 生态中缺乏成熟的 SaaS 替代品
- 自建提供了完全的定制控制

**但有一个领域应该重新考虑：前端监控和错误追踪**。自建一个前端监控系统（错误捕获、性能追踪、用户会话回放）的成本与使用 Sentry（或类似产品）的收益相比，采购的 ROI 更高。

## 最终判断

这个代码库的技术架构是健康的——crate 分层、事件驱动、SFU 设计、存储选择都是合理的。但项目层面的「元架构」存在结构性缺陷：

**分析覆盖率和实现覆盖率之间的差距才是真正的架构缺口。**

当分析文档数量（395）超过前端代码量（18 个文件）、分析文档行数（~102K）超过前端代码行数（~4.3K）的 23 倍时，这意味着资源正从「产出」流向「分析」。这不是文档驱动开发——这是分析替代开发。
