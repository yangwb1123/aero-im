# 架构分析：Aero IM

## 1. 架构评估

### 当前架构的优势

该系统在几个方面具有不同寻常的高质量工程水准，值得首先加以明确：

**清晰的分层和关注点分离。** 16 个 crate 的层次结构几乎是无环图——`aero-common` 作为叶子节点，`aero-bus`/`aero-storage`/`aero-auth` 作为基础设施层，IM 和直播领域 crate 位于其上，而 `aero-server` 作为组合根节点。这在 Rust 工作区中是一项罕见的成就（没有循环依赖，没有 `dev-dependency` 黑客技巧）。依赖方向是单向的。

**事件驱动骨架设计精良。** NATS JetStream durable consumer（`im.room.*`）+ ephemeral consumer（`live.stream.*`）的双重模式体现了一个清晰的设计决策：房间事件需要 at-least-once 语义（持久性 critical），而直播事件可以承受丢失（ephemeral 允许每个实例进行全扇出）。每个 subject 的时间序单调序列号（`bus/seq.rs`）是一个很好的细节——它在不依赖分布式时钟的情况下实现了客户端去重。

**Redis 用于集群状态，而非进程内内存。** 这是另一个正确的决策——presence、stream viewer 计数和 call roster 都使用 Redis sorted-sets 和 TTL 过期。避免了跨实例缓存一致性的问题。

**异步预算控制的 AI 管道。** `AiWorker` 的预算系统（`KeyedCostBudget` + 全局 `CostBudget`，带 weighted all-or-nothing + 60 秒窗口）展示了对 AI API 调用实际成本影响的细致理解。预算耗尽时选择 `defer`（而非丢弃或失败）是一种优雅的降级。

**未经测试的热路径上的防御性编码。** SFU 媒体层（`SfuMediaSession` + `SfuForwarder` + `CallBridge`）在生产中并未完全连接，但其结构设计表明已预见到跨节点 RTP 中继——这是经常被忽视的架构前瞻性。

### 关键架构限制

**1. 后端/前端能力差距（主要问题）。**

这是验证文档的 5 个方向中反复出现的主线，但让我从架构角度更精确地说明：

| 维度 | 后端 | 前端 |
|-------|--------|-------|
| 路由模块 | 122 个 `fn routes()` | 0 个独立路由控制器 |
| API 端点 | 376 个 `.route()` 调用 | ~50-55 个 `api.js` 方法 |
| 状态管理 | 类型化、事务化、有审计 | 无状态管理——`context.js` 中的全局 `state` 对象 |
| 表单验证 | 服务端 trim + 长度限制 + 类型检查 | 无客户端验证 |
| 测试 | 1,406 个 `#[test]` | 0 个测试 |
| 数据模型 | 完整的 ORM（sqlx）+ 迁移版本控制 | 零本地存储（刷新即消失） |

这并非渐进式差距——这是一个**架构断裂**。后端是一个生产级系统（有事务、审计、预算控制、迁移、集群状态），而前端是一个调试客户端（目的是探索 API，而非服务用户）。

**2. 实时 WebSocket 帧的覆盖缺口与 API 缺口同样严重。**

验证文档正确指出了 API 覆盖率，但低估了 WS 帧问题。后端事件模型暴露了：

- 11 个 `RoomEvent` 变体（`Message`、`Edited`、`Deleted`、`Reaction`、`Read`、`Typing`、`Notify`、`NotifyBatch`、`Interaction`、`Call(CallEvent::*)`、`Poll`）
- 9+ 个 `StreamEvent` 变体（`Chat`、`Gift`、`Viewers`、`Status`、`HypeTrain`、`Raid`、`PointsRedeemed`、`GoalProgress`、`GoalReached`、`Prediction*`）
- `CallEvent` 子枚举（`Invite`、`Join`、`Roster`、`Offer`、`Answer`、`Ice`、`Caption`、`End`）

而 `render.js` 中的 `onServerFrame` 处理大约 20 种帧类型。缺口大约为 30-40%。对于基于 WebSocket 的实时应用来说，**这与 REST 覆盖率缺口同等关键**——无声丢弃的帧意味着功能完全对用户不可见。

**3. 全局单例模式阻碍了前端模块化。**

前端的所有 18 个模块通过 `context.js` 中的三个共享全局变量耦合：

```javascript
// context.js - 所有状态的单一事实来源
export const state = {};  // 可变全局
export const els = {};    // DOM 缓存
export const ws = {};     // WebSocket 引用
```

这意味着任何模块都可以改变 `state`，任何模块都可以读取 `state`，且没有封装边界。`app.js` 中的事件处理代码直接操作 DOM，绕过了任何虚拟 DOM 或模板系统。这导致了：

- 不可能对单个模块进行单元测试（没有可 mock 的 DI 边界）
- 重构一个模块可能会破坏任何其他模块（紧耦合）
- 没有变更检测或响应式更新（手动 DOM 操作）

**4. 管理能力在架构上缺失。**

后端有 20+ 个专门的管理模块（`channel_roles.rs`、`workspace_security.rs`、`legal_holds.rs`、`moderation_bot.rs`、`webhook_admin.rs`、`sso.rs`、`saml.rs`、`scim/`、`subscription_tiers.rs`、`info_barriers.rs`、`ip_allowlist.rs` 等），但前端完全没有管理界面。这不是遗漏——这是一个**架构空白**。管理界面需要一个不同的路由模型（嵌套布局、权限门控组件、侧边栏导航层次结构），这无法融入当前的聊天优先的 DOM 结构。

**5. 文档与实现严重不一致。**

`web/README.md` 声称“无已读回执、无编辑/删除、无附件、无通知”——但这些都在 `api.js` 和 `app.js` 中实现了。这表明工程纪律方面存在系统性问题：**实现变更时不会更新其文档**。

对于一名 AI agent（或任何新工程师）来说，`README.md` 是首次接触点。如果 README 不可信，那么心智模型从一开始就有缺陷。这导致重复工作（在已有实现的基础上进行构建）和回归（由于对边界的不正确假设）。

### 架构债务与技术债务

| 债务类型 | 位置 | 严重程度 | 备注 |
|----------|------|----------|------|
| 🔴 关键 | `web/` — 零测试 + 全局单例状态 | 高 | 阻碍所有重构；任何更改都可能产生回归 |
| 🔴 关键 | `web/README.md` — 陈述与实际实现矛盾 | 高 | 误导新贡献者；导致重复工作 |
| 🟡 重大 | `crates/aero-server/src/` — 181 个文件在同一 crate 中 | 中 | 组织良好但体积较大；可以拆分为领域子 crate |

| 🟢 轻微 | `config.toml` — 端口 3030 而非 8080（文档标准） | 低 | 部署一致性；与 `config.example.toml` 不匹配 |
| 🟢 轻微 | `AGENTS.md` 锚约定——智能但脆弱 | 低 | 约定强，但规则复杂，增加了认知负荷 |

## 2. 扩展方向

### 方向 A：前端架构产品化（P0 — 最高优先级）

**为什么需要：** 38% 的 API 覆盖率使得后端投资实际上被浪费了。用户无法使用管理工具、审核界面、流设置、通话控制或 AI 摘要——这些都属于后端已实现且功能完整的部分。这是投资回报率直接损失。

**核心挑战：**
1. **状态管理。** 从全局 `context.state` 迁移到带有单向数据流的可预测状态容器。挑战不在于选择库（vanilla JS 也可以做到），而在于在不重写所有 18 个模块的情况下进行增量迁移。
2. **组件化。** 当前 DOM 操作代码（在 `render.js` 和 `app.js` 中具有紧密耦合的 `el.innerHTML = ...`）需要迁移到具有清晰属性/事件接口的可组合组件。需要一种策略来就地升级较大的 DOM 树，同时保持交互性。
3. **测试基础设施。** 零测试意味着没有安全网。引入测试需要：(a) 模块解耦（模拟 WS、模拟 API），(b) 测试运行器（node 或浏览器），(c) 为立即重构创建回归护栏。

**架构变更：**

```
web/
├── app/                    # 新的应用程序目录（增量）
│   ├── state/              # 带有 action/reducer 模式的状态管理
│   ├── components/         # 具有 props/events 的可组合 UI 组件
│   ├── pages/              # 路由级页面组件（聊天、管理、设置）
│   └── services/           # API + WS 抽象层
├── app.js → app/main.js    # 引导入口点
├── render.js → deprecated  # 逐步淘汰
└── context.js → deprecated # 逐步淘汰
```

**对现有系统的影响：** 低到中。后端无需更改。前端迁移可以增量进行——新的页面（管理、设置）使用新架构构建，而现有的聊天视图在当前系统与新状态层连接后保持不变。

**选项 A：渐进式状态引入**（推荐）
- 引入一个简单的发布/订阅状态层（vanilla JS，< 100 行）
- 增量地将 `context.state` 访问迁移到新的 store
- 不影响现有功能

**选项 B：完整的 SPA 框架（Lit/Svelte）**
- 更高的前期迁移成本
- 但长期开发人员效率更好
- 与新系统相比，与当前非打包设置匹配较差

---

### 方向 B：管理控制台架构（P0 — 与 A 并列优先级）

**为什么需要：** 20+ 个管理路由模块没有任何 UI。对于管理员来说，系统实际上不可操作——他们无法管理用户、审核内容、配置 SSO、设置频道角色或查看审计日志。每个缺失的管理功能都会导致运营问题的积累。

**核心挑战：**
1. **路由模型不同。** 管理界面需要嵌套布局（侧边栏 → 部分 → CRUD 表），这与当前聊天 DOM 不兼容。需要第二套路由方案。
2. **权限门控。** 每个管理功能都有不同的角色要求（`WorkspaceRole::Owner`、`StreamModerator`、特定于频道的角色）。UI 需要根据用户权限进行条件渲染。
3. **数据表范式。** 大多数管理视图都是 CRUD 表（搜索、排序、分页、批量操作）。这需要可重用的表组件——目前不存在。

**架构变更：**

```
web/
└── admin/                  # 管理控制台根目录（新架构）
    ├── layout.js           # 管理 shell（侧边栏、页眉、面包屑）
    ├── pages/
    │   ├── users/          # 用户管理（CRUD、角色、停用）
    │   ├── streams/        # 流管理（审核、报告）
    │   ├── workspaces/     # 工作区设置（SSO、SCIM、安全）
    │   ├── content/        # 内容审核队列
    │   └── billing/        # 使用情况和计费（如适用）
    ├── components/
    │   ├── data-table.js   # 可重用表格（排序、过滤、分页）
    │   ├── form-fields.js  # 字段验证
    │   └── action-bar.js   # 批量操作 UI
    └── admin.js            # 入口点 + 路由调度
```

**对现有系统的影响：** 中。管理路由通过 Axum 的 `.merge()` 无缝集成，因此后端路由无需更改。前端需要一个单独的 SPA shell（独立的路由、独立的 JS 包），这可以在不触及现有聊天功能的情况下实现。

**安全边界：** 后端已经强制实施了 `assert_room_access(participant, room)` 和 `member_role()` 守卫。前端必须在 UI 中复制此权限模型（隐藏不可见的操作），但绝不能信任它——所有变更为都会在后端重新验证。

### 方向 C：WebSocket 帧覆盖的实时完整性（P1）

**为什么需要：** 如前所述，~40% 的 `ServerFrame` 变体在前端被静默丢弃。这包括 `Interaction` 事件、某些 `CallEvent` 子类型、`Poll` 事件和 `StreamEvent` 子集。用户看不到他们应有的 UI 状态更新，导致行为错误（“我点击了投票但看不到结果”，“通话正在响铃但 UI 未显示”）。

**核心挑战：**
1. **帧类型漂移。** 后端事件模型独立于前端发展。每当添加新的 `RoomEvent` 变体时，除非有纪律性地检查前端，否则前端会静默丢弃它。需要一个类型安全的契约。
2. **处理程序注册。** 当前的 `onServerFrame` 是一个大型 match 语句。任何框架（如 NestJS）中都不存在处理程序注册模式，其中处理程序是独立注册的。

**架构变更：**
- 在 `ws.js` 中引入帧处理程序注册表（`Map<string, Handler>`），取代 `onServerFrame` switch 语句
- 每个 JS 模块注册其自己的处理程序（`ws.on('message', ...)`）
- 为未处理的事件添加降级。如果某个帧类型没有注册处理程序，则记录警告（而非静默丢弃）
- 考虑前端事件契约测试——一个列出预期帧类型的 JSON 文件，在 CI 中针对 Rust 的 `RoomEvent` 枚举进行验证

**对现有系统的影响：** 低。WS 层的变化是前端架构内的重构。后端无需更改。

---

### 方向 D：工程基础设施和测试（P1）

**为什么需要：** 零测试 + 陈旧文档 + 无类型检查的组合意味着前端架构的每一次更改本质上都是重构。没有安全网。引入基础设施是释放其他所有开发的前提条件。

**核心挑战：**
1. **测试现有代码。** 遗留代码（`app.js`，有 1009 行紧耦合 DOM 操作）本就不适合测试。解决策略：新的代码路径必须是可测试的；旧的代码路径在有意义时进行集成测试。
2. **文档同步。** `web/README.md` 需要准确，最好作为系统文档而非“调试客户端”标签。需要一个流程，在实现更改时更新 README。
3. **CI 集成。** `scripts/web-check.sh` 存在但是一个轻量级检查。eslint 存在但未强制执行。需要完整的 CI 管道：eslint（警告）→ tests（必需）→ 大小检查。

**架构变更：**
```
web/
├── __tests__/              # 新测试目录
│   ├── unit/               # 纯函数测试
│   ├── integration/        # WS/API mock 集成
│   └── fixtures/           # 测试数据 JSON
├── eslint.config.js        # 已存在，更新规则
├── package.json            # 新的（用于测试运行器，非打包工具）
└── vitest.config.js        # 测试配置（或等效工具）
```

**对现有系统的影响：** 无。基础设施添加不会改变现有功能。

**测试策略选项：**

| 选项 | 优点 | 缺点 |
|--------|--------|-------|
| **Vitest**（推荐） | 原生 ESM 支持；快速；良好的 DOM mocking（jsdom） | 添加 npm 依赖项 |
| **Node 原生测试** | 零依赖；使用 `--experimental-test` | 功能较少；生态系统不发达 |
| **Playwright** | 真实浏览器 E2E 测试 | 更慢；更重；对于单元测试来说过度了 |

### 方向 E：CSS 架构现代化（P2）

**为什么需要：** 1236 行的全局 `style.css` 文件已经达到了在没有命名约定或范围限制的情况下可维护的极限。这已经导致了 ~6 个特定于聊天的媒体查询，没有管理 UI 的断点。任何新页面（管理、设置、流浏览）将需要更多的样式，如果没有结构，将会冲突。

**核心挑战：**
1. **无范围限制。** 没有 CSS 模块、Shadow DOM 或 BEM 约定。选择器冲突是不可避免的。
2. **无设计标记。** 颜色是重复的（`#6366f1` 和 `#a855f7` 存在于多个地方），间距值很随意，并且没有排版比例。
3. **断点非结构化。** 媒体查询仅存在于聊天布局中。所有屏幕尺寸都没有系统性的断点策略。

**架构变更：**
- 在 `style.css` 顶部引入 CSS 自定义属性（设计标记）
- 添加 BEM 命名约定（或类似的后处理类名生成）
- 将管理样式分离到 `admin.css`（或使用 CSS `@import` 拆分）
- 添加管理 UI 的断点策略（桌面优先：管理是桌面端的，移动端为“紧急操作”）

**对现有系统的影响：** 低。CSS 更改是纯添加/重命名。`style.css` 重构可以增量进行，同时保留现有选择器。

## 3. 接口设计原则

### 核心原则

**1. 前端-后端契约必须明确。**

当前，前端通过阅读 Rust 源代码（`RoomEvent` 枚举定义）来反向推导帧类型。需要一个显式契约：

```
方案 A: 共享 TypeScript 类型定义 → 为 Rust + JS 生成代码
  - 优点：单一事实来源
  - 缺点：添加构建步骤；与当前无构建设置不匹配

方案 B: OpenAPI + JSON Schema 用于帧类型
  - 优点：标准工具；独立于语言
  - 缺点：需要维护；可能不同步

方案 C: 前端拥有的事件注册表 + CI 验证（推荐）
  - 优点：无构建步骤；增量可行；CI 捕获漂移
  - 缺点：手动列出；非自动生成
```

**推荐方案 C 用于第一阶段**，因为可以在不触及构建系统的情况下增量引入。方案 A 可以稍后演进。

**2. 模块边界必须清晰。**

每个 JS 模块应：
- 导出一个清晰的公共 API（函数、类），而非可变状态
- 不直接操作其他模块的 DOM 元素
- 通过发布/订阅层（或稍后的 store）进行通信
- 拥有一个尽可能小的单元测试表面（纯函数优先）

**3. 向后兼容性策略。**

由于 `web/` 在当前状态下是一个调试客户端，我们可以在不破坏生产用户的情况下重构它（据我所知还没有生产用户）。然而，`api.js` 和 `ws.js` 中已有的 API 签名应保持稳定，这样实验性集成不会中断。策略：

```
第 1 层：保留 api.js 的公共 API 签名（fetch 包装器签名）
第 2 层：内部重构（在 api.js 中交换 fetch → 带有拦截器的 fetch）
第 3 层：弃用旧签名并迁移消费者
```

### 抽象层

当前缺失的：

| 层 | 当前状态 | 目标 |
|-----|-------------|--------|
| **状态管理** | `context.js` 中的全局可变 `state` | 带有 action dispatch 的不可变 store |
| **API 层** | 直接的 `fetch` 调用 | 带有拦截器（auth、retry、logging）的 API 客户端 |
| **WS 层** | 带有固定处理程序的原始套接字 | 具有模式匹配和降级的处理程序注册表 |
| **组件层** | `innerHTML` 直接赋值 | 具有属性 + 生命周期方法的可组合函数/类 |
| **路由层** | 隐式（由 app.js 处理） | 显式路由表，延迟加载 |

引入新的抽象层**不应一次性完成**。一个好的顺序是：

1. **WS 处理程序注册表**（首先：最简单，最大影响）
2. **API 客户端层**（其次：为测试提供模拟边界）
3. **状态管理**（第三：为组件化解除耦合）
4. **组件系统**（第四：建立在状态之上）
5. **路由层**（第五：为管理页面启用）

## 4. 技术选型

### 引入新的依赖项

| 依赖项 | 目的 | 评估 |
|--------|---------|----------|
| **测试运行器**（Vitest / Node test） | 前端测试 | **高价值**。零测试是不可持续的 |
| **Playwright**（可选） | E2E 测试 | **中等价值**。在单元测试覆盖关键路径后 |
| **TypeScript** | 类型安全 | **中风险**。需要构建步骤。不建议现在使用 |
| **Lit** | Web 组件 | **中价值**。标准化的组件模型。可用于新 UI 而非现有 UI |
| **eslint**（已存在） | linting | **高价值，低风险**。已存在；需要强制执行 |
| **Prettier** | 格式化 | **低风险**。可以与 eslint 同时添加 |

### 不必要的依赖项（不推荐）

| 避免 | 原因 |
|----------|--------|
| React/Vue/Svelte | 需要构建步骤；与当前的 ESM 无构建方法不匹配 |
| Tailwind | 与现有 CSS 不兼容；增加了一类新的技术债务 |
| Redux/Zustand | 对于当前状态，vanilla 发布/订阅已经足够 |
| Webpack/Vite | 添加了构建步骤、配置、依赖树 |

### 自建与采购

| 决策 | 推荐 | 理由 |
|--------|----------|---------|
| 状态管理 | **自建**（~100 行发布/订阅） | 简化；无依赖项；易于理解 |
| 组件系统 | **轻量级使用 Lit** | 标准化；~10KB gzip；互操作 |
| 测试运行器 | **采购 Vitest** | 成熟；ESM 优先；良好的 DOM mocking |
| 管理 UI 框架 | **自建**在 Lit 组件之上 | 特定领域（CRUD 表格、表单、布局） |

### 构建管道决策

当前的无构建设置是一个优势（零工具链、简单部署），不应轻易放弃。然而，以下情况值得进行权衡：

| 保持无构建 | 添加构建步骤 |
|-------------|----------------|
| 更简单的部署 | 更好的 DX（HMR、Types） |
| 零工具链 | 树摇 |  
| 快速迭代 | 导入映射兼容性 |
| 与后端集成兼容 | TypeScript 支持 |

**建议：保持无构建以部署核心聊天功能。如果/当管理控制台需要更丰富的 UI 模式（JSX、CSS 预处理程序），则为管理控制台添加单独的、基于构建的入口点。** 双轨方法（无构建的聊天 + 基于构建的管理）是可行的，因为它们是独立的 SPA shell。

## 5. 实施路线图

### 优先级分类

| 级别 | 描述 | 示例 |
|-------|-------------|---------|
| **P0** | 必须拥有；所有其他工作都依赖于它 | 测试基础设施、状态管理、WS 注册表 |
| **P1** | 核心产品价值；直接影响用户 | 管理控制台 P0 页面、帧覆盖率补全、文档修复 |
| **P2** | 质量改进；降低维护成本 | CSS 架构、管理页面 P1、性能优化 |

### 阶段 1：基础设施（4-6 周）

**目标：** 建立前端工程基础设施，以实现后续阶段的协调开发。

| 工作项 | 交付物 | 依赖项 |
|-----------|------------|--------------|
| **测试基础设施** | Vitest + jsdom；第一个 ~20 个纯函数测试（api.js 工具函数、WS 重连逻辑） | 无 |
| **WS 处理程序注册表** | 用处理程序映射替换 `onServerFrame` switch 语句；添加未处理帧检测 | 无 |
| **状态管理精简版** | 发布/订阅 store；增量迁移 `context.state` 读取 | 无 |
| **文档修复** | 更新 `web/README.md` 以反映实际情况；添加帧类型索引 | 无 |
| **CI 强制执行** | eslint 作为阻塞 CI 检查；添加测试运行器 | 测试基础设施 |

**风险：** 增量采用可能陷入半重构状态。缓解措施：新的状态代码必须使用新的 store；旧的代码可以保持原样。如果旧代码没有被触及，它永远不会被强制迁移。

### 阶段 2：实时完整性 + 核心 UX（6-8 周）

**目标：** 关闭 WS 帧覆盖率缺口；补全核心聊天功能中的缺失功能。

| 工作项 | 交付物 | 依赖项 |
|-----------|------------|--------------|
| **帧覆盖率补全** | 为所有 `RoomEvent` 和 `StreamEvent` 变体添加 WS 处理程序；UI 测试覆盖率 | 阶段 1（WS 注册表，测试） |
| **交互/投票 UI** | 投票渲染和投票，交互指示器 | 帧覆盖率补全 |
| **通话 UI 补全** | 通话邀请界面、通话中控制、字幕显示 | 帧覆盖率补全 |
| **附件 UI** | 文件/图片上传 UI（后端已有 `BlobStore`） | 无 |
| **通知 UI** | 通知面板、徽章、偏好设置 UI（后端已有 `notif_prefs.rs`） | 状态管理 |

**风险：** WS 帧覆盖率分析可能揭示设计问题（某些后端事件模式不适合前端渲染）。缓解措施：尽早做帧覆盖率审计，在阶段 1 中识别棘手情况。

### 阶段 3：管理控制台 MVP（8-10 周）

**目标：** 为最高价值的管理功能交付一个工作的独立管理 UI。

| 工作项 | 交付物 | 依赖项 |
|-----------|------------|--------------|
| **管理 Shell** | 带有侧边栏、导航、认证门控的管理布局 | 阶段 1（状态管理） |
| **P0：用户管理** | 用户列表、角色分配、停用、会话管理 | 阶段 2 |
| **P0：内容审核** | 审核队列、操作日志、批量操作 | 阶段 2（帧覆盖率） |
| **P1：流管理** | 活动流、流信息、聊天审核模式 | 阶段 2 |
| **P1：安全设置** | SSO 配置、SCIM 日志、IP 白名单、webhook 管理 | 阶段 2 |

**风险：** 每个管理页面都需要与 20+ 个后端管理模块集成。后端路由身份验证模型（`assert_room_access`、`member_role`）需要在前端正确复制。缓解措施：为管理 UI 创建一个专门的测试套件，使用实际后端响应。

### 阶段 4：CSS 现代化 + 产品化打磨（4-6 周）

**目标：** 修复 CSS 架构问题；打磨 UI 以实现一致、可访问的体验。

| 工作项 | 交付物 | 依赖项 |
|-----------|------------|--------------|
| **CSS 属性** | 在 style.css 顶部提取设计标记 | 无 |
| **BEM / 作用域** | CSS 命名迁移（增量） | 无 |
| **管理 CSS** | 管理布局的新 CSS 文件（表、表单） | 阶段 3 |
| **可访问性** | 键盘导航、ARIA 属性、对比度审核 | 所有阶段 |

### 路线图时间线

```
第 0-6 周  阶段 1（基础设施）          → 解锁所有后续工作
第 4-12 周 阶段 2（实时完整性）        → 与阶段 1 重叠；依赖于其基础
第 10-20 周 阶段 3（管理控制台 MVP）   → 建立在阶段 1+2 的基础上
第 16-22 周 阶段 4（CSS + 产品化）     → 打磨收尾阶段

总计：~22 周用于完整的前端产品化
```

### 关键缓解策略

| 风险 | 可能性 | 严重程度 | 缓解措施 |
|------|----------|-----------|--------------|
| 前端重构破坏现有功能 | 中 | 高 | 增量迁移；所有现有测试通过后才继续；分阶段推出 |
| 管理枚举不足；范围蔓延 | 高 | 中 | 将管理 P0 限定为用户管理 + 内容审核；稍后添加其余的 |
| 后端 API 在阶段 3 期间发生变动 | 中 | 中 | 为管理 UI 编写集成测试，在 CI 中捕获 API 更改 |
| 团队对 vanilla JS 架构不熟悉 | 低 | 高 | 记录清晰；保持简单；避免不必要的抽象 |
| 性能（大型 DOM，无虚拟化） | 低 | 中 | 在阶段 2 中进行负载测试；如果必要，为消息列表添加虚拟滚动 |

---

### 总结

Aero IM 的后端架构（16 个 crate、事件驱动、NATS 骨干网、Redis 集群状态）坚实且具有生产级质量。前端架构（18 个模块、~4,100 行 vanilla JS、零测试、全局状态）是一个调试客户端。

验证文档的 5 个方向是正确的。这里的架构建议是：

1. **保持后端不变。** 后端架构已经良好。
2. **优先考虑前端基础设施（阶段 1）高于所有其他工作。** 没有测试、状态管理解耦和 WS 契约，任何前端重构都是在没有安全网的情况下进行的。
3. **采用双轨前端架构。** 核心聊天（无构建、最小更改）+ 管理控制台（新架构、共享组件）。这避免了对现有功能的风险投资。
4. **为前端契约创建系统性的合规机制。** API 覆盖率和 WS 帧覆盖率应被跟踪为 CI 指标，而非一次性审计。
5. **将 README 准确性视为关键绩效指标。** 如果实现与文档不一致，该文档是主动有害的。

后端与前端之间的产品化差距是真实的，并且很大。但这也是一个明确且可衡量的任务——128 个 `.merge()` 对 0 个管理页面，1,406 个 `#[test]` 对 0 个。度量标准很明确，修复路线图是直接的。它只需要纪律性和时间。
